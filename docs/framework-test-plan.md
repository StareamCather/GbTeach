# 框架验收与观测流程

## 分层验证

1. `python3 -m unittest discover -s tests -v`：验证版本匹配、依赖判断、课包错误隔离、模板与个人练习、进度分离和自有进程清理。模拟器不参与这些单元测试；Linux 进程组检查在其他平台显式跳过。
2. `python3 -m gazeboteach --smoke-fixture tests/fixtures/diagnostic`：使用新的临时练习副本启动真实服务端并执行模型行为验收，结束时自动清理。
3. `python3 tests/integration_probe.py --gui --terminals --report /tmp/gazeboteach-framework.json`：同时运行两个真实仿真，通过仿真时间测量暂停隔离、单步、模型复位和客户端恢复，最后检查会话令牌下无存活进程。
4. `python3 -m gazeboteach --gui-check --screenshot /tmp/gazeboteach-window.png`：启动真实 Qt 窗口并保存自身截图，再进行界面检查。

这些命令由主任务在 ikaros 执行。文档列出的是检查方法，不能用方法说明替代实际通过记录。

## 诊断场景的算法

场景仅有离线地面、光源和边长 0.4 m 的动态方块。验收先暂停仿真，使位姿修改不会在读回前被重力改变；将方块质心抬至 2.4 m 后读取真实位姿，验证控制通路。接着恢复物理时间，轮询实际模型位姿，要求方块在有限时间内落到 z≈0.2 m。该高度来自半边长，容差允许接触求解误差。

该诊断属于框架 fixture，不计入第 01 课及任何正式课程数量。

## 双会话隔离检查

两个会话使用相同世界和模型名称，分别持有独立 Gazebo Master、ROS Master 和 Ignition partition。仅暂停第一个，读取两个世界的真实统计时间：第一个必须不推进，第二个必须继续推进。随后只在第一个世界推进 25 步，检查其时间约增加 25 ms；在暂停状态移动方块并重置模型，检查初始位姿恢复且仿真时间保持。

这种检查能够发现仅隔离 Master 端口、却遗漏 Classic 命令所用 Ignition partition 的问题。检查从每个会话的完整环境执行命令，不能依赖操作者当前终端的全局默认环境。

## 进程清理检查

单元测试创建一个属于测试会话的短命父进程和长驻子进程，同时创建无会话令牌的对照进程。父进程退出后停止会话，子进程必须结束，对照进程必须仍存活。测试始终只清理由自身创建并记录的进程。

真实集成检查最终按每个会话令牌查找同用户非僵尸进程；发现残留则失败，不以服务端退出代替所有组件清理完成。GUI 和终端检查需要真实 X11 会话，未启用相关参数时不能标记为图形或终端验收通过。

## 人工与图形检查边界

自动测试能确认真实窗口进程启动、Qt 截图生成、命令效果和资源清理。字体、正文可读性、按钮排列、窗口遮挡等需要检查实际截图。GUI 编辑器的操作教学和学习者是否真正掌握概念属于课程验收，不由框架启动测试代替。
