# 原生状态日志：记录一次运动，再读取和回放它

本课让橙色方块在真实 Gazebo Classic 11 中下落，用 Gazebo 自带的记录器生成 `state.log`，再让另一个真实 `gzserver` 从这份日志回放。你要交叉核对三个来源：录制时的原生世界状态、日志实际保存的状态、回放服务端实际呈现的状态。

这里最需要分清的是“回放状态”和“重新做实验”。状态回放读取已经保存的结果；重新运行控制程序则再次产生输入，由物理引擎重新计算运动。二者能回答的问题不同。默认实验不需要 ROS，也不需要编写插件。

## 先补齐三个概念

`gzserver`运行世界、物理与服务端通信，`gzclient`显示三维场景和界面；关闭一个图形窗口不等于关闭服务端。模拟时间描述世界进展，墙钟时间描述电脑实际等待多久。状态日志保存世界描述与一系列带时间的状态，文件里的一个状态样本也不是屏幕渲染的一帧。

若刚接触本课程，先完成第1课的启动和暂停、第8课的固定物理步长，以及第12课的进程与 Gazebo Transport。Transport 是 Classic 自身的消息通信机制，本课使用的消息不是 ROS 话题。无需先学完前六种插件，也无需先安装额外模型。

官方背景可查 [Classic 组件概览](https://classic.gazebosim.org/tutorials?tut=components)、[记录与回放教程](https://classic.gazebosim.org/tutorials?tut=logging_playback)。本课固定使用 Classic 11；现代 Gazebo 的 `state.tlog`、ECS 系统与命令格式不适用于这里。

## 三种“再看一次”保存了什么

| 方法 | 保存的主要内容 | 再次执行时发生什么 | 能直接证明什么 |
| --- | --- | --- | --- |
| 本课原生 state.log | 初始世界描述、实际保存的世界状态与源时间 | Gazebo 读取状态并应用到回放世界 | 已保存状态能否被原生回放恢复 |
| 重新运行控制程序 | 程序、配置与输入；还需另行管理初态和外部条件 | 物理引擎再次计算运动 | 在给定条件下再次计算得到什么结果 |
| 视频或截图 | 渲染后的像素 | 播放图像 | 当时某个视角看到了什么 |

状态日志也不是所有 Transport 或 ROS 消息的通用录包。本课的 JSON 报告用于保存检查证据，它不是 Gazebo 回放的数据源。把报告里的 z 坐标读出来，再逐次发送设置位姿命令，可以做一种自定义动画，却不能据此宣称完成了原生 `state.log` 回放。

## 本课世界与两个参数

世界名为 `lesson32`，包含地面 `floor` 与自由方块 `falling_cube`。地面顶面 z=0，方块边长 0.4 m、质量 1 kg，初始质心 z=2 m、初速度为零；重力为 `(0,0,-9.8)` m/s²。ODE 最大步长为 0.001 模拟秒。光源、颜色与几何均在本地 `world.sdf` 中定义，不依赖联网下载 `model://` 模型、网格或贴图。

默认个人参数为：

```json
{"record_steps": 300, "encoding": "zlib"}
```

| 参数 | 含义与范围 | 不应混淆的量 |
| --- | --- | --- |
| record_steps | 本次录制推进的正常物理步数；整数 100..800 | 不是每隔多少步记录一次，也不是日志状态条数 |
| encoding | 原生 chunk 编码；zlib、txt 或 bz2 | 不是物理精度或传感器采样率 |

默认 300 步对应 0.3 模拟秒的物理进展。机器较慢时墙钟等待可以更长，不能把“等待 0.3 秒”当作准确推进 300 步。较长的 800 步实验可能包含触地，后半段要用接触求解解释。

第31课的 `record_every_steps` 控制课程插件保留样本的间隔；本课的 `record_steps` 控制录制的总时长。名称相近，算法位置不同。本课没有增加一个每 N 步写 JSON 的插件来替代原生记录器。

## 先预测原始运动，再预测回放

首次接触前，连续自由落体模型为：

```text
v(t) = -9.8*t
z(t) = 2 - 0.5*9.8*t²
```

以 h=0.001 s 的半隐式欧拉作为理想离散参照：先更新速度，再用新速度更新位置，完成 N 次积分后有 `z_N = 2 - 9.8*h²*N*(N+1)/2`。

| 完成积分数 N | 模拟进展 | 连续预测 z | 理想离散预测 z |
| --- | --- | --- | --- |
| 100 | 0.1 s | 1.951 m | 1.95051 m |
| 200 | 0.2 s | 1.804 m | 1.80302 m |
| 300 | 0.3 s | 1.559 m | 1.55753 m |

这些是算法预测，实际测量由本次运行产生。方块平放接触后的支撑质心约为 0.2 m，理想首次触地时间约为 `sqrt(2*(2-0.2)/9.8)≈0.606 s`；接触后不能继续外推抛物线。

对回放的预测不同：在日志实际存在的源时间与迭代处，回放实体应与该条记录按原生恢复流程得到的位置相符。比较目标首先是保存的数据，不是重新用自由落体公式算一个z。原始仿真与日志之间还存在文本序列化精度、采样阶段和时间边界等问题；原生状态序列化并非无限精度快照。

目标SDK对模型和link的位置先按四位小数处理，但模型字段再以三位有效数字输出，link字段以四位有效数字输出。例如假设原值为1.23456，先处理为1.2346，再分别写成1.23与1.235。这是序列化示例，不是本课预填的测量。回放怎样组合这两层状态，需要看下一节的原生恢复顺序，不能只取model/pose当作最终模型位置。

## 一次记录经过哪些环节

```text
个人 world.sdf、parameters.json 和工具源码
  → 准备程序验证输入，用本机 Classic 11 SDK 编译原生观察工具
  → 平台在本课私有 master 下启动 gzserver -u world.sdf
  → 查询原生世界，暂停并完整复位，确认本次录制初态
  → 向原生 LogControl 发送 start、绝对路径与 encoding
  → 观察原生 LogStatus，确认实际输出路径
  → 有限推进物理；同时保存源时间、迭代与实际实体检查点
  → 原生 World 采集状态，LogRecord 分批编码并写入 state.log
  → 发送 stop；等待本次记录完成收尾，检查文件闭合及稳定
  → 原生 LogPlay 解码实际 SDF 记录；返回原始帧与检查结果
  → 第二个私有 master 启动真正的 gzserver -u -p state.log
  → 用原生回放控制推进，读取回放服务端的时间与实体位姿
  → 分别保存原始检查点时间T与实际日志时间S，核对两层位置与真实回放
```

原始服务端根据重力与接触进行物理计算，记录器只读取其状态。回放服务端进入 Classic 的日志路径：`LogPlay::Step`读下一条 SDF 状态，`World::SetState`应用它，再完成相应世界更新。该路径关闭物理引擎积分，因此方块的回放位姿来自日志。关闭物理积分并不表示程序中没有更新、通信或渲染活动。[Classic 11 世界实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/World.cc)给出了这两条运行路径。

一个model可以包含多个link。link是具体刚体，canonical link是模型用来关联自身运动的基准刚体；本课只有`body`一个link，其相对模型的初始位置与旋转均为零。原生恢复先设置model保存的位置，再设置各link保存的世界位姿；设置canonical link还会重新确定父模型的位置。因此本课回放最终模型位置等于日志中`body`的世界位置，可能与较粗的model/pose文本值略有不同。这由[Model.SetState](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/Model.cc)和[canonical link的位姿更新](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/Entity.cc)共同决定；多link或有相对偏置的模型不能直接套用“模型位置等于body位置”。

课程同时保留日志的model位置、body世界位置和实际回放位置。它分别检查两种文本序列化，再按canonical link恢复语义比较真实回放；发现这两层不同，不应直接放宽误差把它们混为一项。

## 开始录制与只读检查

在平台选择本课，开始个人实验，等待准备和服务端就绪。打开 Gazebo 可以看到初始暂停的橙色方块与灰色地面。在本课终端执行：

```sh
python3 lab.py ready
python3 lab.py record
python3 lab.py inspect
```

`ready`检查个人配置和构建摘要，并读取本课原生世界；它不会为了制造样本而推进物理。`record`会暂停、完整复位并录制新的有限实验，因而会改变原始世界的时间与运动状态。它不是旁观当前任意运动，也不承诺恢复进入命令前的任意位姿和速度。开始前先保留需要的旧输出。

`inspect`读取最近一次实际记录，检查闭合 XML、编码、原生 SDF 帧与时间范围；`inspect --file <绝对路径>`可检查指定日志。输出包含真实`raw_sdf`，不是从位姿重新拼接的示意数据。它不重新运行落体，也不修改记录中的坐标或时间。先确认日志存在并完整，再讨论记录了多少状态；“目录中有文件”不足以证明录制完成。

每个数值检查点依次读取“原生统计→实体→原生统计”。复位或回放定位可能恰好发生在这些独立查询之间；工具最多用6墙钟秒重新读取，直到前后统计都为暂停、源模拟时间相同且迭代计数相同，才接受中间的实体结果。重新读取不重发复位、步进或定位命令。每次尝试保留`stable`或`pending_transition`状态；超时则报告当前阶段与诊断文件，不把尚未一致的读数当作成功快照。

要单独熟悉原始世界的暂停和步进，可使用：

```sh
python3 lab.py pause
python3 lab.py step --steps 100
python3 lab.py ready
```

这里推进的是原始物理世界。已经走过 100 步后再走 100 步，累计进展为 200 步，第二段不是从静止重新释放。正式 `record`会按自己的复位流程建立录制初态。

空闲记录器不会持续发布状态，所以状态查询发送仅含`start:false`的原生`LogControl`，请求实际`LogStatus`。原生处理器只在start为true时启动、stop为true时停止，因此这个探测不开始或停止记录，也不改变暂停状态。显式false使消息具有非空字节，避免Classic Transport丢弃完全空的消息；工具会在有限时间内重复这种只读请求，直到收到实际反馈。开始录制、停止录制、复位、物理步进及回放定位等改变状态的请求仍只发一次，不用查询重试规则重放操作。

## 停止请求、状态反馈与文件完成

发出停止消息、收到一条 `LogStatus`和得到完整日志，是三个不同层次。消息可能仍在路上，接收端也可能先看到旧状态；原生记录器还需要排空状态队列、完成最后的编码写入、写出 `</gazebo_log>`并关闭文件。不能在发送停止后立即把当前字节数当作最终结果。

本课结合后续原生状态中的输出路径、文件稳定性与完整 XML 检查确认收尾。`LogStatus`本身没有 `running`或 `paused`布尔字段，不能凭空读取这样的原生字段。它的 size 还有单位，反馈也可能计入缓冲；最终文件字节数应读实际文件。

字段名也需要结合实现解释：该版本 `LogStatus.sim_time`由记录器运行时长生成，不能替代世界状态里的源模拟时间。300 步录制的物理时长要查原生 `WorldStatistics`或日志中的 `state/sim_time`。[原生状态消息定义](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/msgs/log_status.proto)和[记录器实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/util/LogRecord.cc)是判断字段含义的依据。

不要通过手工补上结束标签让失败录制通过。本版本 `LogPlay::Open`对部分缺尾文件会尝试追加结束标签；所以课程在调用它以前先验证原始 XML，随后核对源文件摘要。能被某个读取器修复，不代表最后一批状态完整保存。

## 日志内部：完整世界、状态与 chunk

`state.log`的外层是 XML，根元素为 `gazebo_log`。原始 header 保存 `log_version`、`gazebo_version`与 `rand_seed`。日志格式版本、Gazebo 软件版本和内部 SDF 版本属于三种不同的兼容性信息，不应把 `1.0`理解成 Gazebo 1。

第一条 SDF 记录提供完整世界描述；后续 SDF 记录主要包含 `state`，带有模拟时间、真实运行时间、墙钟时间、迭代以及实际保存的实体状态。本课把世界源时间换算为整数纳秒用于匹配，同时保留原始 SDF 与原始消息。接收端单调时钟只说明消息何时到达观察进程。

`chunk`是一次编码和写入的批次，可以包含多条 SDF 记录。默认 zlib 和可选 bz2 先压缩这一批文本，再以 Base64 放进 CDATA；txt 直接保存文本。它不是“整个文件是一份可直接 unzip 的压缩包”。改变编码改变存储形式，不改变已经生成的 SDF 文本含义。

“差分”和“关键帧”也要准确理解：Classic 11 的世界记录线程计算前后状态差来判断是否有变化，但实际入队保存的是当前过滤后世界状态，并非只保存数值增量、再靠读者逐条相加恢复。最初的完整世界描述承担初始化作用；本课没有视频式“每隔固定帧插一个关键帧”的配置。初始描述与后续状态仍不能任意互换，后续状态不包含完整建模定义。

默认原生记录周期不对每步另加固定正周期限制，但状态变化判断、工作线程、序列化与插入/删除事件仍影响最终样本序列。即使方块尚在下落，也不保证每个物理迭代都有一条保存状态；静止区间同样可以稀疏。第一条保存状态可能晚于初态，回放统计的起止时间应按日志读取，不能一律写成从0开始。不要要求chunk数、SDF记录数、状态条数、模型状态数和物理迭代数相等，也不要把两个样本之间的缺口自动补成测量。[原生日志读取实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/util/LogPlay.cc)说明了按SDF记录读取与按chunk解码的区别。

录制800步时，原始世界仍必须真实到达0.8模拟秒；若方块此前已经落稳，记录器可能不再新增状态，日志末时刻可以早于0.8秒。本课不会为此补一帧或改写旧时间。对原始检查点T，只取不晚于T的最后一条实际日志状态S，再要求其model与body两层位置均等于原始T位置各自序列化后的值；任一不符就失败。S=T标为`exact`，S<T标为`retained_state`，并保留T−S。后者表示较早已保存状态在当前保存精度下仍能代表这次位置检查，不表示日志真的在T采样，也不证明整个间隔内的连续运动或速度。

回放只定位到真正存在的S，要求原生读回时间也是S。报告分别显示`original_sim_time_ns`、`recorded_sim_time_ns`、`match_kind`与`retained_interval_ns`；原始世界最终时间与日志末时刻也分别保留。不要把0.8秒的原始物理进展写成“日志一定能播放到0.8秒”。

## 日志没有替你保存什么

旧教程会概括世界状态可包含位姿、速度、加速度与力；具体到本课目标版本，默认流式输出没有打开 link 速度记录，加速度、wrench及关节状态也不能按那段概述一概保证存在。应先看实际日志字段。对象在 API 内存中能提供某种属性，不代表该属性一定写入了这份文件。[LinkState序列化](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/LinkState.hh)和[ModelState采集实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/ModelState.cc)给出了具体边界。

传感器的定义可能随初始世界描述出现，但这不等于记录了每张RGB图像、深度数组、激光扫描或IMU测量消息。回放中某个传感器重新产生数据，也是在当前渲染/传感器环境中生成，不能宣称就是原来的字节序列。本课没有传感器，自动数值验收比较世界时间与方块模型的三维位置；原生实体输出保留完整位姿，但本课不将其称为已验证六自由度姿态或速度复现。

初始 SDF 中引用的模型、网格、贴图或插件库，也不等于文件内容自动打包进状态日志。Classic 有额外的资源记录选项，但不替代对实际资源完整性的检查。本课直接采用本地几何与颜色，使运行和回放不需要下载资源；迁移自己的复杂场景时，要连同依赖、版本、路径和许可证另行整理。

## 启动真正的原生回放

```sh
python3 lab.py playback
python3 verify.py
```

`playback`使用最近一份完整日志启动独立的真实回放服务端，读取其原生统计、实体位姿与回放时间范围，完成有限检查后清理自己创建的进程。原始世界必须已经暂停；正式record结束会保持暂停。`verify`会重新录制一次，再完成读取与真实服务端回放的完整链路，所以它会完整复位原始世界。查看报告中的实际检查项和错误；编译成功、日志可解析与回放状态匹配分别证明不同事情。

原始实验与回放使用不同的私有 `GAZEBO_MASTER_URI`，并为相关通信配置各自隔离环境。原生全局记录器话题 `/gazebo/log/control`与 `/gazebo/log/status`必须发往正确的 master；只看两个世界同名 `lesson32`不能说明连对了进程。原始世界保留供比较，回放不会接管它。

底层原生启动形式是 `gzserver -u -p <state.log的绝对路径>`；`-u`表示初始暂停，`-p`表示读取日志。本课工具负责实际路径、独立端口、超时和所属进程管理，不需要再手工启动一个未隔离的重复服务端。

需要观察真实回放窗口时，在具有图形显示环境的本课终端执行：

```sh
python3 lab.py playback --gui --seconds 6
```

它真正启动连接回放master的`gzclient`，先等待窗口启动，再展示各检查点，最后保留指定墙钟秒数供观察，然后自动关闭自己创建的回放窗口和服务端。`--seconds`默认6，范围0.5..20；这是最后的观察停留时间，并非整个命令的总耗时。可用20秒练习时间线，期间手工操作可能改变自动检查需要的暂停或定位状态；先完成一次自动检查，再做图形练习，并如实区分结果。

GUI演示在启动和停留期间最多每0.1墙钟秒检查一次自己创建的服务端与客户端进程，并在定位前、读回后和清理前再次检查；提前退出会报错并保留`gui_liveness`诊断。这个检查证明进程在检查时仍存活，实际窗口画面及控件效果仍需图形观察。在最后自动清理之前手工关闭回放窗口，也会被记作提前退出。

普通平台的“打开 Gazebo”对应原始实验，不能仅凭橙色方块的相同外观把两个窗口混同。原生日志回放界面提供播放、暂停、前后步进与时间线等操作；步进针对保存样本，样本间模拟时差可能不同，不保证每次都是1ms。[官方回放界面说明](https://classic.gazebosim.org/tutorials?tut=logging_playback)给出了这些控件的用途。是否已看到窗口、实际操作了哪些控件，要按这次图形观察另行记录。

回放时间线定位是在已有样本中选择状态，不为任意指定时刻重新计算一段物理，也不保证对两条记录做插值。要证明某时刻的数值相等，应读回实际落到的源时间和迭代，再找对应日志记录。

## 两个单变量实验

实验A：保留 `encoding=zlib`，只把 `record_steps`从300改为200，保存并重载，再完整录制与回放。预测总物理进展由0.3变为0.2模拟秒，较早时刻的运动规律不变；终点位姿相应不同。不要预测文件必定减少三分之一，固定世界描述、元数据、压缩批次与实际状态数都会影响字节数。

实验B：恢复300步，只把 `encoding`从zlib改为txt，保存并重载。预测世界步长、重力和相同源时间处的运动规律不变，文件中的chunk编码与存储字节数改变。两次录制的墙钟时间和批次可以不同，所以整个文件的哈希通常不同；不同哈希不自动表示位姿不同。比较实际解码状态，再比较真实回放读回。

可再单独比较bz2，但每次只改一个变量。整理记录时分列：配置、原始世界检查点、原生日志时间范围/状态数/实际字节数、日志摘要、回放master与进程身份、回放读回及残差。压缩率和墙钟耗时都是本次实测量，不能在运行前预填成一个漂亮数字。

## 如何判断复现到了哪一层

“读取同一份日志”可以复现已保存的状态序列，却不能自动恢复控制器内存、插件私有变量、随机数引擎的完整内部状态、未保存的速度或外部网络输入。因此本课不把 `state.log`当作可任意续算的完整仿真检查点。

重新计算还会受到物理引擎版本、求解器设置、时间步长、模型资源、浮点运算和输入调度影响。随机种子有助于记录条件，但不单独保证跨环境逐位一致。回放的渲染结果也可能受显卡、驱动、分辨率与视角影响。保存状态匹配、重新求解轨迹匹配和像素匹配应分别验证。

本课自动检查覆盖数值和文件链路；真实GUI窗口、时间线操作与可见运动需要另做图形观察。只运行无GUI的verify，不能写成“已经人工验证所有回放控件”。截图可以确认实际窗口和可见状态，不能替代原生时间、迭代与实体数据。独立扩展若没有另行实测，就应标明未验证。

## 故障诊断与独立挑战

| 现象 | 先检查什么 |
| --- | --- |
| start已发送但没有日志 | 正确私有master、原生记录器订阅、实际LogStatus路径、可写目录与准备摘要 |
| stop后文件缺结束标签 | 本次录制是否完成收尾；保留错误与原文件，不补标签伪装成功 |
| 状态条数少于物理步数 | 变化检测、状态时间与实际录制范围；不要先假设丢了N条数据 |
| chunk只有几块却录制了很多步 | chunk是批次；继续用原生LogPlay拆出SDF状态 |
| 日志没有速度或传感器图像 | 实际序列化字段和记录类型；不能从旧教程概述推断存在 |
| 原始z、日志model/pose与回放z不同 | 时间/迭代、两种序列化精度、body世界位姿和canonical link恢复顺序；保留各层原值与残差 |
| 检查点报告pending_transition或超时 | 查看checkpoint诊断中的阶段、master、前后暂停/时间/迭代及实体结果；只读重采样不等于再次执行操作 |
| 回放画面不动 | 正确回放窗口、暂停状态、是否已到日志末尾、原生日志时间范围 |
| 原始世界已到0.8秒，回放时间线更早结束 | 查看最后保存状态与原始终点的两层位置、retained_state及时间差；静止后可能不新增状态 |
| 看到了方块却没有回放证据 | 进程命令行是否-p、world_stats是否有log_playback_stats、读回位姿是否匹配 |
| 改参数后结果仍旧 | 保存并重载，核对本次准备摘要和最近产物路径 |
| 复杂场景换机后资源缺失 | 初始SDF中的URI、实际本地依赖与软件版本；state.log不自动包含所有依赖字节 |

挑战一：不改代码，提出三条能区分“日志能解析”“服务端进入原生回放模式”“实体恢复了保存状态”的独立证据，说明为什么只读一个布尔结果不够。

挑战二：只改record_steps为700，先预测日志可能跨过哪类运动阶段，再实际录制。把接触前与接触后的分析分开，并解释为什么日志状态数不必刚好700；不要把所有采样差异都归因于网络丢包。

挑战三：设计传感器数据复现方案。先列出需要原样保存的消息、时间戳、坐标系、标定与外部资源，以及状态回放和消息回放如何对齐，再决定是否实现。本课的无传感器日志通过验收，不证明该扩展已经完成。

各命令按实际状态确认完成并设置有限等待。原始step默认100、范围1..1000步，要求进入时已暂停；reset先暂停并发送一次完整世界复位，等待原生时间回到0与方块z回到2m，结束保持暂停；它没有仅凭一次位置读回证明独立速度测量。resume会恢复原始世界连续计算，之后仍需主动pause。

发生错误时先保留报告、原生日志和服务端输出；清理只针对本工具创建的回放进程。工具用本次token、用户ID及进程启动时间确认身份，先有限等待正常终止，仍未退出才强制结束已确认所属进程，并把结果写入ownership.json。不要使用`killall`、`pkill`或删除整个用户日志目录处理本课故障。超时也不等于请求未执行，尤其不能不断重发步进命令来凑出期望结果。
