# 仓储机器人：从一束激光到一次可复查的过门任务

一辆小车从仓库一侧出发，接近关闭的门，在门前停车，等门真正让出通道，再驶向另一侧目标并停住。这条路线很短，却能检验前面各课是否真正接起来：轮子有没有推动小车，激光有没有看见门，坐标和时间有没有对齐，开门请求有没有产生真实运动，以及任务结束时小车是否确实减速停止。

本课环境是Ubuntu 20.04、Gazebo Classic 11.15.1、ROS 1 Noetic、Python 3.8；平台界面使用Qt 5.12。它是一条已知直通道上的有限任务。程序使用明确的状态和测量条件组织动作，不包含全局路径规划、SLAM或完整仓储调度系统。学完后，你应能沿着原始消息、状态转移、关节读回和轨迹解释一次成功，也能说明一次失败为什么停在门前。

有限状态机，简称FSM，是把“当前在做什么”和“何时进入下一步”写清楚的一种组织方式。例如WAIT_DOOR表示此时只能等待；只有读到门已足够打开、前方确实通畅并持续一段时间，才允许进入PASS。状态名称帮助人理解，真正决定行为的是每条转移的测量条件。

## 先看完整信息流

```text
个人world.sdf + parameters.json + 当前源码
  → prepare.py核对输入、构建本课原生门插件和通信工具
  → 私有Gazebo/ROS会话加载真实轮式机器人、通道和滑门

CPU RaySensor → ROS /warehouse/scan ─┐
实际世界位姿 → /warehouse/odom ─────┼→ mission.py有限状态机
实际接触     → /warehouse/bumper ────┤       ├→ /warehouse/cmd_vel
门关节q、速度、施力读回 ────────────┘       │   → 左右轮电机 → 轮地接触 → 车身运动
                                           └→ 开门目标
                                               → door_plugin.cc的PD力 → 滑动关节 → 门运动

原始消息 + 转移事件 + 实际状态
  → 每次任务独立目录 → CSV、扫描投影SVG和结果
```

小车为`warehouse_bot`，门为`warehouse_door`，门关节为`slide_joint`。速度接口是`/warehouse/cmd_vel`；里程计、扫描、碰撞和轮关节状态分别为`/warehouse/odom`、`/warehouse/scan`、`/warehouse/bumper`、`/warehouse/joint_states`。`/lesson36/state`是可供后订阅者读取的状态JSON。接口出现只说明ROS图中登记了连接，还要继续检查时间戳、数值、所属实体及真实运动。

任务服务`/lesson36/start`、`/lesson36/reset`使用[Trigger](https://github.com/ros/ros_comm_msgs/blob/noetic-devel/std_srvs/srv/Trigger.srv)，`/lesson36/enable_door`使用[SetBool](https://github.com/ros/ros_comm_msgs/blob/noetic-devel/std_srvs/srv/SetBool.srv)。本课`lab.py`封装这些入口，终端继承应用创建的私有ROS和Classic连接。不要再启动另一份roscore或gzserver来“补齐”接口，也不要用全局清理命令结束其它实验。

## 两条真实执行链

小车沿用第33课的轮式结构：左右轮通过关节连接车身，后部支撑参与接触。ROS差速插件把前向速度v和偏航角速度Ω换成左右轮速度目标，再由受限关节电机和轮地接触推动模型。轮子转动、车身位移和扫描变化应能互相对应。物理过程不通过反复写车身位姿来制造。默认轮电机力矩上限为5 N·m，轮地摩擦系数为0.8；本课的门施力参数不会改变这两项。

轮半径r=0.10 m、轮距b=0.36 m，理想无滑时：

```text
ωL = (v − Ωb/2)/r
ωR = (v + Ωb/2)/r
```

默认v=0.25 m/s直行时两轮目标各为2.5 rad/s。`Twist`本身没有时间戳；发送零Twist表示请求轮速目标归零，不能证明车身速度立即等于零。接触求解、起停过渡和有限轮电机力矩都会影响实际响应，零目标也可能伴随少量被动接触漂移。[2.9.3差速插件实现](https://github.com/ros-simulation/gazebo_ros_pkgs/blob/2.9.3/gazebo_plugins/src/gazebo_ros_diff_drive.cpp)

长时间等待时，几毫米每秒的被动漂移也可能累计为厘米级位移；独立验收同时检查零目标、实际低速、随等待时长计算且封顶的位移包络，以及向门方向的最大推进不超过0.01 m，不能把“停止目标”解释为精确位置保持，也不能把放宽测量容差称为修复了物理漂移。

门是受约束的可动刚体，沿+Y方向滑开。关节闭合目标q*=0 m，打开目标q*=1.25 m。插件在每个物理更新读取实际位置q与速度q̇，计算并限幅施力：

```text
F = clip(120(q* − q) − 20q̇, −Fmax, +Fmax)
```

这里120的单位是N/m，20的单位是N·s/m，默认Fmax=20 N。P项推动位置误差缩小，D项抑制运动速度，限幅使起步力有限。门的质量、惯量、阻尼、关节约束和碰撞共同决定实际开启过程。门板下缘在地面上方0.05 m，滑动轴由固定在world的anchor约束，不靠门板拖地形成阻力。开门请求改变的是目标；请求确认和门已经打开是两件事。插件持续使用`Joint::SetForce`，任务中的q来自实际关节读回。[Classic 11.15.1关节API](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/Joint.hh)、[SDF滑动关节与限位](https://sdformat.org/spec/1.6/joint/)

## 小车看见了什么，坐标又来自哪里

激光是一层水平二维扫描。默认361束覆盖−90°到+90°，角间隔0.5°，量程0.06～8 m，目标更新频率10 Hz。每个有效距离rᵢ对应方向`θᵢ=angle_min+i·angle_increment`，局部点为`(rᵢcosθᵢ,rᵢsinθᵢ)`。CPU射线从传感器位置出发，返回该方向最近可命中的物理几何；关闭的门遮住门后的物体，门打开后露出的远点才有机会出现。扫描平面没有扫到的低矮障碍和被遮挡区域，不能从“没有点”直接推断为可通行。[Classic RaySensor](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/sensors/RaySensor.cc)

先按实际量程与`isfinite`过滤点，再做投影。`+Inf`、`−Inf`与`NaN`不是三个普通距离：分别涉及无回波/超量程、过近与无效情况。无回波不应被画成一圈“真实墙面”，无效扇区也不能作为前方通畅的肯定证据。[REP-117](https://github.com/ros-infrastructure/rep/blob/master/rep-0117.rst)

本课坐标树为：

```text
world → warehouse/odom → warehouse/base_footprint → warehouse/laser
         单位静态边          差速插件动态边             固定安装边
```

激光相对base的安装平移是(0.15,0,0.2202) m，轴向与车体一致。`frame_id`是坐标身份，不是坐标变换本身。只有传感器、odom与TF使用了相符的frame和时间，点才能放到同一幅图里。

差速插件明确使用`odometrySource=world`，所以odom位置取自Gazebo真实世界位姿；`world→warehouse/odom`为单位变换，出生时的x偏移已经在odom→base中。这里的odom是受控教学中的真值来源，不是独立轮编码积分定位；投影图的位置精度也继承了这个条件。REP-105解释一般移动机器人中odom与map的职责，本课没有估计map→odom，也没有借此证明真实仓库定位已经解决。[REP-105原文](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)

扫描投影应尽量对应**扫描时刻**的位姿。本课保留odom时间序列，为扫描选取不晚于它、且最多早120 ms的最近实际odom；没有符合条件的样本就拒绝该帧投影。CSV同时保存两个原始stamp，因此这个保持近似可以复算和评价，并不声称精确插值到了扫描时刻。默认0.25 m/s下，120 ms对应约0.03 m直行位移量级，转向还会带来角误差。

进一步的做法是等到扫描前后都有odom，再插值平移与最短角差；本课没有实现这一步。直接把旧扫描配上“刚收到的最新odom”，也不保证时间对齐。当前CPU ROS包装的`time_increment`和`scan_time`均为0，表示这条实现按同一时刻处理一帧；不要据此除以0求频率，也不要补造逐束机械扫描时刻。[2.9.3 CPU包装](https://github.com/ros-simulation/gazebo_ros_pkgs/blob/2.9.3/gazebo_plugins/src/gazebo_ros_laser.cpp)、[LaserScan时间字段](https://github.com/ros/common_msgs/blob/noetic-devel/sensor_msgs/msg/LaserScan.msg)

输出的CSV与SVG展示真实扫描点在已知位姿下的投影。程序不读SDF墙轮廓来填点，也不把预测距离当传感器回波。图中可能叠有多个时刻的门位置，动态门会留下不同位置的点；这不等于静态占据地图。这里没有扫描匹配、位姿优化、回环或建图后规划，不能把这张投影图称为SLAM结果。

## 每一次转移都要有理由

| 当前状态 | 小车与门的动作 | 进入下一状态的实际条件 |
| --- | --- | --- |
| SCAN | 零速度，建立本轮新扫描与位姿证据 | 取得所需新数据并经过初始观察段，约0.5模拟秒 |
| APPROACH | 沿通道朝门行驶 | 前向扇区近距小于0.65 m，或位置已到x>−0.85 m的门前保护线 |
| WAIT_DOOR | 小车持续零目标，请求开门 | 实测q>1.10 m且前方距离>1.20 m，连续满足0.30模拟秒 |
| PASS | 通道条件允许时前进过门 | 车体参考位置x>0.65 m后结束过门阶段并请求关门 |
| GOAL | 向x=2.20 m目标区前进并减速 | 进入目标容差后转入停车观察 |
| STOPPING | 持续零目标，观察实际运动 | 真实x与2.20 m差小于0.06 m、\|y\|<0.10 m、平面速度<0.028 m/s、\|偏航角速度\|<0.08 rad/s且门q<0.05 m，连续满足0.50模拟秒 |
| FAILED | 持续零目标，保留失败原因和日志 | 需学习者明确复位/恢复，再发起新任务 |

门关节条件与激光条件各有用途：q说明执行器实际让出了多大行程，前向扫描说明此刻传感器所见的通道。只看门的开关布尔量可能过早放行；只看单条射线又可能遗漏车身宽度、轮子或门框。当前固定门洞宽1.20 m，小车含轮碰撞的横向外廓约0.37 m；门板宽1.20 m，q>1.10 m时其靠近通道中心的边缘已移到y>0.50 m。这个几何预测解释开度保护的量级，实际还要结合侧向误差、朝向和扫描。改变车宽、门宽或扫描安装后必须重新核对间隙，不能直接沿用数值。

0.30 s连续清空条件是稳定时间保护：一次清空读数不会立即放行，期间条件丢失就要重新累计。接近门的0.65 m、放行的1.20 m使用不同阈值，服务于不同阶段，减少在边界读数附近反复切换。它们仍不能替代实际刹车距离与几何校验。

WAIT_DOOR的等待上限为6模拟秒。超时应进入FAILED并停在门前，不能凭“应该已经开了”继续前进。全程另有40模拟秒、90墙钟秒上限，odom反馈停滞超过3墙钟秒也触发失败。数据缺失时先请求零目标；实际碰撞、错误frame、时钟回退等保护会记录具体原因。正常结束、失败与异常收尾都请求零速度；物理是否停住仍须看读回。

## 实验一：先建立一次健康运行

在应用加载本课后，从本课操作终端执行：

```sh
python3 lab.py ready
python3 lab.py bootstrap
python3 lab.py run
```

ready检查当前会话和输入，不推进物理；bootstrap在零目标下至少推进0.60模拟秒以取得真实初始消息，随后暂停。run先恢复物理并等待新反馈，再发起有限任务，结束后暂停。运行中观察小车是否先接近、再停住，门是否经过一段真实运动才让出通道，小车是否在目标附近减速并停止。读取本轮输出的实际目录，不能仅看终端最后一行状态。完成后若要再次从出生点运行，先执行`python3 lab.py reset --world`；常规reset保留成功终点，start会拒绝从门后开始。

需要单独观察消息时，先在另一个本课终端订阅，再运行有限动作：

```sh
rostopic echo -n 1 /warehouse/scan
rostopic echo -n 1 /warehouse/odom
rostopic echo -n 1 /lesson36/state
```

暂停期间新订阅者不一定得到动态scan或odom；状态接口是latched，也不表示它包含新的物理采样。记录消息stamp、frame、实际ranges长度和任务身份。不要把一个旧的SUCCEEDED状态误认作刚刚完成的新任务。

成功证据应包括：状态转移按顺序发生；门关节真实行程达到放行条件；过门前有实际零目标等待段；小车通过门区且抵达目标；零目标之后真实末速降到有限阈值内；本轮扫描点来自实际消息。是否存在话题、是否发过开门请求、是否画出SVG，都不能单独证明成功。

## 实验二：关门故障必须先留下失败

先明确恢复世界初态，再关闭本课门的自动开启权限：

```sh
python3 lab.py reset --world
python3 lab.py enable-door --enabled false
python3 lab.py run
```

预期小车仍能采样和接近，随后在WAIT_DOOR持续请求零速度。门保持关闭，q与前向距离不能满足放行条件；等待超时后本轮为FAILED，run会以非零状态退出并暂停，这正是本轮应保留的故障结果。核对失败目录中WAIT_DOOR的持续时间、小车位置与末速、门q、命令记录及失败原因。真实门前停车是这次试验的目标；小车冲门、到达目标或把超时写成成功，都需要排查。

保留这份失败目录，再恢复自动门并明确建立新一轮任务：

```sh
python3 lab.py reset
python3 lab.py enable-door --enabled true
python3 lab.py run
```

不带`--world`的reset先暂停，清除上一轮任务状态与数据缓存，恢复门控制的默认权限并请求闭门，建立新的任务记录；它保留机器人真实位置。失败后小车留在门前，恢复任务从实际当前位置继续，仍须重新采样、等待实际开门、过门、到达并停止。`reset --world`则明确调用Gazebo的reset_simulation，同时恢复物理初态与模拟时间；重新加载本课也会建立新世界。两者都不是任务控制产生的运动，不能算进过门轨迹。

单独把enable改回true不会把旧失败报告变成成功，也不会自动重写旧日志。恢复是否有效，只能由新任务的真实轨迹、门关节与末速证据判断。这个步骤沿用第35课“保留失败→单因素恢复→真实重跑”的方法。

## 实验三：一次只改一个因素

先将车速从0.25改为0.20 m/s，门上限保持20 N，保存并重载。预测两轮直行目标由2.5降为2.0 rad/s，3.80 m恒速量级由15.2变为19.0 s。比较两次APPROACH、PASS和GOAL段的真实位移/时间与门前停车位置；门本身的PD参数未变，不能把整轮时间变化全归因于门变慢。

恢复默认车速后，只把门施力上限20改为12 N并重载。预测大误差起步阶段更容易受到较低上限约束，但开启时间是否明显增加要读实际q(t)、q̇(t)。当前事件保存的施力值来自门命令确认时最近一次物理更新，不是连续F(t)曲线；要研究完整施力过程需另外订阅原生门状态并留档。若某段计算力本来就低于12 N，两种限幅可能在该段没有区别。不要同时修改门质量、PD系数和等待时间来“做出明显结果”。

每轮记录参数、输入指纹、开始状态、模拟时间、到门时刻、清空稳定段、目标误差与真实末速。使用不同目录保留原始数据；若一次超时，保留它并解释是哪条测量条件没有满足，不删掉失败样本再统计。

## 沿链路查问题

| 现象 | 先读哪些证据 | 区分的原因 |
| --- | --- | --- |
| cmd_vel有消息，小车不动 | pause、真实轮角、轮关节名、接触与电机上限 | 收到目标与实际轮地驱动不同 |
| 开门请求已确认，门还没让开 | q、q̇、F、enabled、实际推进时间 | 收到命令、受力运动、达到间隙是三个阶段 |
| 门已开却一直WAIT_DOOR | 同时刻q和前向扇区、连续清空计时、数据新鲜度 | 执行器开度不足、仍有遮挡或数据过旧 |
| 点云像跟着小车拖尾 | 扫描stamp、选定前序odom的时间差与安装偏移 | 保持近似误差、错误接收时刻或安装变换 |
| 图上没有门后物体 | 当时门位置、扫描高度与遮挡 | 没被看见不等于空间不存在物体 |
| 归零后坐标仍稍变 | 零命令、轮角、真实速度窗口和接触 | 目标归零不等于无惯性、无被动漂移 |
| 复位后马上跳状态或超时 | 新任务身份、时间是否回退、旧缓存与稳定计时 | 旧时间段的数据混进新任务 |
| 磁盘参数已改而行为不变 | build/warehouse.json、源码/产物指纹与当前会话 | 保存输入和运行实例采用输入不同 |

世界复位会使`/clock`回退。跨越回退点的scan/odom不能继续配对，旧数据新鲜度、超时起点和“已连续通畅0.30 s”也都失效。任务级reset与Gazebo世界复位是两层操作，记录清楚采用哪一种；运行中时钟回退会使任务失败，随后明确reset并重新采样，不能让旧任务悄悄继续。

start还检查“当前模拟时间−消息stamp”：scan须在[−0.001,0.30] s、odom须在[−0.001,0.15] s内，防止复位后排队到达、时间戳仍属于旧时间段“未来”的消息通过新鲜度检查。

## 验收与挑战

```sh
python3 verify.py
```

课程内verify.py会明确复位世界，实际运行一次正常任务，检查完整状态序列、接触计数、实测点数量及投影算式。它会改变当前初态并建立新任务，结束后保持暂停；关门失败与恢复按照实验二分别执行并保留证据，独立开发验收也单独覆盖这两轮真实运行。检查报告中的当前结果、路径和未覆盖范围；没有采集到的数据保持缺失。数值自动验收与GUI观察分开记录：未亲眼看过窗口，就写“完成原生数据验收，GUI观察未做”，不能把加载成功写成看过真实过门动画。

挑战一：选WAIT_DOOR→PASS这一条转移，列出支持它的扫描stamp、所用odom时刻、q、前向距离和稳定时间。再选一帧不满足条件的数据，解释为什么那一帧不能放行。

挑战二：在关闭门失败中找出最后一次非零Twist、第一次零Twist、进入WAIT_DOOR及FAILED的时刻，比较请求停止与实际低速段。用数据解释停车距离，指出0.65 m阈值为什么不能直接当作车头到门的净距。

挑战三：从投影CSV选一束真实有效射线，手算其局部点、加激光安装偏移、用所记录前序odom的朝向旋转并平移到world。核对SVG中的对应位置和两个stamp的差，再指出哪些步骤依赖本课world来源odom。构思等待后一帧odom后再插值的改进方案，说明缓存、最短角差和拒绝条件应怎样处理。

挑战四：保留一份失败和一份恢复成功的目录，写一张比较表：输入身份、门权限、状态序列、门前位置、实际开度、目标误差、实际末速与人工观察。解释为什么“启用门”是恢复动作，而新一轮真实完成才是恢复证据。

本课实现流程为：**核对当前输入与原生组件→建立私有世界与ROS接口→持续接收真实扫描、odom、轮角、接触和门关节→选取时间差受限的实际前序odom并投影实测点→以有限FSM发出轮速与门目标→在门前零目标等待真实间隙稳定→实际过门与目标减速→零目标下通过真实末速确认停车→保留成功或失败全程数据→明确恢复并以新任务重跑。** 小车运动来自轮电机与接触，门运动来自每步PD力，图中的点来自扫描；三条来源都不能被预设轨迹或SDF轮廓替代。
