# 性能与批量实验：让每一行结果对应一次真实物理运行

本课把“看起来运行得快”变成一个可核对的问题：从新建一个无界面的Gazebo服务端，到确认方块完成1模拟秒的下落与接触，一次完整试验用了多少墙钟时间？你将改变方块数量和物理步长，每种组合重做两次，得到带原生读回、计时边界和来源信息的JSON与CSV。

批量实验由独立的真实`gzserver`逐次执行，不把同一世界的多段运动当作独立重复，也不靠公式生成轨迹。本课不需要ROS；应用中的Gazebo窗口是预览世界，批量结果来自另外创建、完成后关闭的服务端。

## 先分清正在测量什么

模拟时间是物理系统走过的时间，墙钟时间是你在机器前实际等待的时间。两者相除之前，必须说明分母从哪里开始、在哪里结束。CPU时间又是进程实际占用处理器的累计时间，等待、休眠与通信可能消耗墙钟却少用CPU。

| 量 | 回答的问题 | 本课怎样使用 |
| --- | --- | --- |
| 原生模拟时间与iterations | 世界实际推进了多少时间、多少次物理更新？ | 检查0、0.2和1.0模拟秒及对应迭代 |
| ODE物理步长h | 每次正常物理更新推进多少模拟秒？ | 比较0.001与0.002 s |
| real_time_update_rate | 世界循环是否按目标墙钟频率节流？ | 批量世界设0，取消这项速率限制 |
| end_to_end_wall_s | 一个新服务端从创建到取得合格终点，需要等待多久？ | 本课主要耗时指标 |
| end_to_end_sim_throughput | 每墙钟秒完成了多少模拟秒的整次任务？ | 实测模拟进展除以上述耗时 |
| 原生RealTime | Gazebo世界自身累计的运行计时是什么？ | 保留原始字段，解释暂停语义；不作为本课分母 |
| CPU时间 | 哪些所属进程实际用了多少处理器时间？ | 本课未采集，不用父Python的CPU时钟代替服务端 |
| GUI FPS、传感器update_rate | 窗口画面或传感器以什么节奏更新？ | 本课批量世界无GUI、无传感器，不测这些量 |

若1模拟秒的任务实际花了W墙钟秒，本课吞吐量为`1/W`模拟秒/墙钟秒。这里的W包含启动、Transport连接、辅助查询进程、两段推进间的暂停和读回，不能将结果命名为“纯ODE实时因子”或“物理引擎每秒更新次数”。数值小于1也不能直接说明ODE本身跑不动实时。

实时因子通常表达同一测量窗口内`Δ模拟时间/Δ实时间`；GUI给出的估计有自己的更新窗口。本课刻意另命名端到端吞吐量，避免把不同窗口放在一张表里直接排名。原生`World::RealTime`在暂停时冻结，而有限multi_step仍能在暂停状态推进物理，所以本课的原生RealTime可能不增长。出现0不能用一个极小数替换后计算巨大RTF。[Classic 11.15.1的World计时与步进实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/World.cc)说明了这个边界。

## 最少背景与前置知识

你需要知道SDF描述世界，`gzserver`负责服务端物理，`gzclient`负责图形界面。可先回看第7、8课的碰撞与求解器、第12课的Transport，以及第31、32课的模拟时间、有限步进和隔离进程。不会C++也可以先完成本课的参数实验；原生辅助程序只负责读写真实Gazebo消息。

本课限定Gazebo Classic 11 / ODE，验收环境以11.15.1为准。不要照搬现代Gazebo的ECS系统、`gz sim`命令或ROS 2接口。官方[Classic物理参数教程](https://classic.gazebosim.org/tutorials?tut=physics_params&cat=physics)介绍步长与求解器；[Classic性能指标教程](https://github.com/osrf/gazebo_tutorials/blob/master/performance_metrics/tutorial.md)区分传感器模拟更新率、墙钟更新率和相机帧率。阅读时不必安装旧教程的额外示例。

## 场景与默认试验矩阵

每个批量世界有静态地面和一组彼此分开的立方体。方块边长0.2 m、质量1 kg，从质心z=2 m、零初速度释放，重力向下9.8 m/s²；地面顶面z=0，平放后的质心约为0.1 m。方块以0.5 m间距固定网格生成，不通过Python随机数选择出生位置；8个是24个网格中的前8个。增加到24个方块改变了刚体与地面接触的总工作量，但不是把方块堆成一座互相挤压的塔。

个人`parameters.json`的默认内容为：

```json
{"counts": [8, 24], "step_sizes_s": [0.001, 0.002], "repeats": 2, "seed": 12345}
```

counts只能是`[8,24]`的非空、无重复整数子集，step_sizes_s只能是`[0.001,0.002]`的非空、无重复子集；repeats为1..3的整数，seed为0..2147483647的整数。参数文件只接受这四个键。列表顺序就是运行顺序，保留顺序有助于解释缓存与机器负载变化。

| 方块数 | 步长 | 到0.2 s的累计步数 | 到1.0 s的累计步数 | 独立重复 |
| --- | --- | --- | --- | --- |
| 8 | 0.001 s | 200 | 1000 | 2 |
| 8 | 0.002 s | 100 | 500 | 2 |
| 24 | 0.001 s | 200 | 1000 | 2 |
| 24 | 0.002 s | 100 | 500 | 2 |

默认共8次新进程试验，顺序运行。次数是参数组合数乘以repeats，不是创建8个同时争抢CPU的世界。每次先到0.2模拟秒，暂停查询全部方块，再推进余下0.8模拟秒，到1.0模拟秒查询接触后的终点。

批量SDF的`real_time_update_rate=0`表示世界不按该频率主动节流，仍然需要真实计算、处理消息并等待查询，不表示瞬间完成、零步长或无限吞吐。ODE的固定步长使`N=T/h`在本课可整除；从0.001改为0.002会把1模拟秒的积分数减半。[PhysicsEngine的更新周期实现](https://github.com/gazebosim/gazebo-classic/blob/gazebo11_11.15.1/gazebo/physics/PhysicsEngine.cc)将非正更新率对应的节流周期设为0。

应用预览世界采用8个方块、h=0.001 s及1000 Hz目标更新率，便于观看。它的运行节奏与批量世界不同，不能从预览窗口的FPS估算CSV中的耗时。

## 先写下物理预测

在首次接触前，连续自由落体模型是：

```text
z(t) = 2 - 0.5*9.8*t²
vz(t) = -9.8*t
```

在0.2 s时，连续预测z=1.804 m、vz=−1.96 m/s。用先更新速度、再更新位置的半隐式欧拉式理解步长影响：

```text
v_k = v_(k-1) - g*h
z_k = z_(k-1) + v_k*h
z_N = 2 - g*h²*N*(N+1)/2
```

| 到0.2模拟秒的步长 | 理想离散z预测 | 理想vz预测 |
| --- | --- | --- |
| 0.001 s | 1.80302 m | −1.96 m/s |
| 0.002 s | 1.80204 m | −1.96 m/s |

表中是公式预测，不是已经取得的测量。两种步长都到相同模拟时刻，位置会因离散化而略有不同。真实检查点来自完成相应步数并暂停后的原生实体查询，不是WorldUpdateBegin里的积分前采样。

理想首次触地时间由`2−0.5*9.8*t²=0.1`估计，约0.623 s。1模拟秒已跨过接触阶段，不能继续使用自由落体公式预测负高度。应查看真实终点是否接近地面、各方块是否仍在自己的网格位置附近；具体有限阈值与本课验收算法见参考页。

不要先预测“24个一定慢3倍”或“步长翻倍一定快2倍”。总工作量还包含启动、查询、碰撞、求解、操作系统调度和缓存；本课短试验中的这些开销可以占很大比例。只能在本次机器、版本、输入和计时边界下陈述实测结果。

## 开始实验与查看预览

在平台选择本课并开始实验，等待个人准备与原生SDK辅助程序构建完成。在本课终端执行：

```sh
python3 lab.py ready
python3 lab.py status
```

ready核对当前个人输入、构建身份和预览世界；status用于只读查看。成功只表示预览与工具就绪，尚未完成批量物理验收。

需要看一小段真实运动时，先从初态开始：

```sh
python3 lab.py reset
python3 lab.py step --steps 100
```

预览h=0.001 s，100步对应0.1模拟秒，结束保持暂停。可以打开Gazebo观察一组方块同时下落，再用`python3 lab.py pause`暂停；`resume`让预览连续运行，`reset`重建真实初态。不要把操作预览的经过时间或画面当成批量某一次trial的数据。

## 运行真实批量试验

```sh
python3 lab.py batch
```

也可直接调用批量入口：

```sh
python3 batch.py run
```

两条命令都实际执行当前个人矩阵。每次运行创建新的UUID归档，每个trial另有自己的SDF、私有通信环境、进程身份与输出。批量工具启动服务端后检查暂停初态，发一次到0.2 s的有限步进，读取自由落体检查点，再发一次余下步进并读取1.0 s终点，最后只关闭这次创建的进程。

物理阶段的完成条件由原生模拟时间与迭代数共同确认；收到几条消息、等了几墙钟秒，都不能替代步数。非幂等命令重复发送会多推进世界，超时后不应手工重发相同步数并把结果接在旧trial上。失败应保留原始目录，诊断后创建一次新试验。

批量试验不会为每步打开GUI，也不会让预览世界替它完成计算。私有`GAZEBO_MASTER_URI`隔离Classic通信，独立partition隔离相应通信发现；每次的HOME与资源路径也有明确边界。世界仅用SDF内基础几何，无需在线下载模型。名称相同不意味着连接到了同一进程，必须核对trial的私有地址与实际进程身份。

## 读JSON和CSV之前，先确认来源

本次结果保存在`build/batches/<本次UUID>/`，主报告为`report.json`，平表为`trials.csv`。其中每行对应一次真实trial，不能拿旧CSV中的成功行填补本次失败。

| 文件 | 应读出的信息 |
| --- | --- |
| parameters.json | 方块数量、步长、独立重复数和Gazebo种子 |
| world.sdf | 应用预览世界；不是所有批量trial的共同物理配置 |
| config.py / prepare.py | 参数验证、原生工具构建、输入与SDK来源绑定 |
| observer.cc | 查询原生统计、物理配置和实体，发送原生有限控制 |
| lab.py / batch.py / verify.py | 预览操作、独立批量运行和物理验收 |
| build/batch_lab.json | 当前个人准备记录与源码、SDK及产物摘要 |
| 每个trial的world.sdf | 本次实际使用的方块数和步长 |
| 每个trial的ownership.json | 实际命令、所属进程及退出检查 |
| 每个trial的native-events.jsonl / gzserver.out | 原生读回、控制过程与实际服务端输出 |
| 每个trial的result.json | 该次结果；失败时也保留已有内容与所有权信息 |
| report.json / trials.csv | 每次结果、耗时和可复核的来源关系 |

先读参数和SDF哈希，再读初态/自由落体/终态原生读回，最后比较耗时。输入相同的重复应生成相同SDF字节；不同trial仍有不同进程、地址和记录。哈希证明字节身份，不证明物理正确。源文件、编译器、Gazebo全版本及实际链接库信息用来界定这份测量来自哪里。

保存个人参数或源码后需要重载项目，再运行ready和batch。正在运行的预览、磁盘源码、已构建辅助程序是不同阶段；不得删除摘要检查来混用新文件与旧实例。

## 如何解释这一次耗时

`end_to_end_wall_s`从创建该trial的服务端进程前开始，到取得一致的最终原生检查点结束。准备阶段的SDK编译不在每个trial的主计时内；服务端启动、连接和试验中的辅助查询在内。服务端收尾另记`cleanup_wall_s`，不塞进主分母。

`startup_readiness_wall_s`帮助识别启动就绪花费，`measured_control_wall_s`帮助识别两段控制与读回花费。它们属于同一次任务的阶段描述，不能重新取一个更短分母，再仍称它为同一端到端指标。报告落盘、CSV汇总和所有trial之间的组织开销也应按实际边界解释；批量命令总等待时间通常不等于某一行的主耗时。

比较相同(count,h)的两次重复，至少保留两条原始值及范围，再讨论中心值。两次不足以估计稳定分布或给出可靠置信区间；本课没有预设硬件速度阈值，也不以哪种组合更快判定成功。热缓存、后台任务与固定运行顺序都可能影响结果，不能只挑最快一次代表整个配置。

无界面服务端省去了本课客户端窗口的显示工作，但它仍执行物理、Transport、日志与工具查询。本课没有同配置的GUI开/关配对计时，因而不声称“headless快了多少”。有相机或其他渲染传感器的世界，即使不启动gzclient，也可能仍需要服务端渲染；本课没有传感器，不能将结果外推到视觉仿真。

## 自动验收与人工观察

```sh
python3 lab.py pause
python3 verify.py
```

验收实际运行当前矩阵，检查每次初态、0.2 s下落、1.0 s终点、原生模拟时间/迭代、私有进程与来源记录，还比较相同输入重复的两个位置检查点。加载成功、程序退出码为0或CSV有8行都不足以单独通过；每个方块都必须有真实物理结果。

verify在批量前后分别只读预览状态，不会替你暂停或恢复它。先执行pause，才能把前后相同的原生时间、迭代与位置用于人工核对隔离；若预览仍在连续运行，它正常继续运动不构成批量串线。当前batch自动核对预览SDF字节没有改变，verify保留前后读回；逐项相等比较需要你另行核对，不能把“有两个快照”写成已经自动验证全部状态相同。

自动数据检查与图形观察分别记录。手工可在预览中观察方块下落、触地与暂停，再核对数值；批量试验本身没有GUI画面。没有实际打开并观察窗口时，只能报告完成了headless数值验收。任何教材预测表都不能替代本次report.json的实测数据。

## 两个单变量对照

先固定counts为`[8]`，保留两种step_sizes_s和repeats=2，运行一份新报告。对照两组在0.2 s处的实测z、位置误差与1000/500总步数，再看端到端耗时。问题是“少一半积分是否在这个计时边界中表现为更短等待，以及物理误差怎样变化”，不是证明普遍的两倍提速。

再固定step_sizes_s为`[0.001]`，counts恢复`[8,24]`，其他参数保持相同。比较同一步长下数量变化，核对每个方块的物理结果和总任务耗时。24/8=3只是实体数量比，不能直接当成CPU、接触数或墙钟比。

seed只传给Gazebo的原生随机数入口；网格位置不依赖它，Python没有调用random来造场景。同种子便于限定原生随机源，却不保证不同SDK、编译选项、线程安排或硬件上的接触轨迹逐位相同。若研究随机扰动，应明确扰动由哪一个随机数生成器产生，并把实际初态另存为证据。

## 沿证据链诊断

| 现象 | 首先检查 | 解释边界 |
| --- | --- | --- |
| 原生RealTime为0，模拟时间已到1 s | paused、iterations与实际方块读回 | 暂停多步可推进物理，不能据此计算无限RTF |
| 步长翻倍但主耗时没减半 | startup、控制查询与重复间波动 | 短任务的固定开销可能占较大比例 |
| 24个方块没有按数量比例变慢 | 相同h、SDF、各trial计时和后台负载 | 耗时不必与实体数线性 |
| 时间达标，方块仍在空中 | 物理是否启用、初态、重力、实体身份 | 不能只用时钟通过物理验收 |
| 终点靠近地面，但没有下落证据 | 0.2 s真实检查点、初态及ID | 静态摆放在地面不等于完成过自由落体 |
| 收到别的世界或旧结果 | 私有master、partition、token、本次目录 | 模型同名不代表进程归属相同 |
| 中途超时 | 服务端输出、native-events与ownership | 保留已取得证据，不补造终点或重发非幂等控制 |
| GUI流畅而CSV耗时较大 | 是否看的是预览；计时是否包含启动 | 窗口FPS与批量任务吞吐测量对象不同 |

## 挑战：给一个有边界的性能结论

用本次CSV制作四行比较表：count、h、每个重复的主耗时、端到端吞吐量、0.2 s位置误差、终点高度范围。每个数字都能追溯到一个trial，再说明计时包含哪些开销。

最后回答三个问题：为什么0.002 s有500步却不保证两倍速度？为什么窗口FPS不能证明积分更准确？为什么重复SDF哈希相同仍需要读取真实物理结果？如果改为堆叠方块、有摩擦滑动或高频传感器，应重新选择误差指标与试验时长，不能照搬本课落体通过条件。

本课运行流程为：**核对个人输入与真实SDK工具→生成组合矩阵→为每个重复创建新SDF与私有服务端→读回暂停初态→有限推进至0.2 s并查询全部方块→推进至1.0 s并查询接触后的终点→按实际时间、迭代、实体和有限物理误差判定→关闭所属进程→保存原始结果与计时边界→汇总CSV。** 预测只参与比较，绝不写回Gazebo或填充缺失测量。
