# GUIPlugin：让真实按钮控制仿真，再用世界状态确认

本课在 Gazebo Classic 的客户端中加入一块 Qt 控制面板。它显示世界模拟时间、迭代次数和暂停状态，提供暂停、继续和推进 N 步三个按钮。按钮负责发出原生控制消息，服务端负责推进真实物理；面板上的文字应来自服务端反馈，不能在点击后自行把时间加到预期值。

场景里只有一只从高处释放的方块和地面。世界 `lesson30` 以暂停状态启动，`falling_cube` 的质心初始高度为2米，边长为0.4米，地面顶面为0。项目不需要 ROS；它使用 Gazebo Classic Transport 和系统 Qt5。

## 先区分三种界面

GazeboTeach 是用于阅读、准备和管理实验的桌面应用；Gazebo 自己还有工具栏和世界面板；本课 GUIPlugin 则是加载进真实 `gzclient` 的一个 QWidget。它们可以控制同一个私有实验世界，但不因此变成同一个程序对象。

| 对象 | 在本课中的职责 |
| --- | --- |
| GUIPlugin / QWidget | 承载文字、按钮和布局 |
| QPushButton 的 clicked 信号 | 通知对应槽函数处理一次操作 |
| Qt GUI 线程 | 创建、读取和更新 QWidget |
| Transport 接收回调 | 接收原生世界统计，缓存数据 |
| QTimer | 在 GUI 线程读取缓存、刷新标签并检查命令是否完成 |
| gzserver | 实际暂停、继续、积分和碰撞 |
| 原生实体及世界统计 | 独立验证方块运动和模拟时间 |

与第29课相比，这次的主要对象是 Qt 控件，不是渲染场景中的 Visual。与第26、27课相比，GUIPlugin 也没有直接持有服务端 World/Model 对象。

不了解 Qt 信号槽，可查看[Qt5 信号槽说明](https://doc.qt.io/qt-5/signalsandslots.html)；不了解 QWidget 的线程约束，可查看[Qt5 对象与线程](https://doc.qt.io/qt-5/threads-qobject.html)。官方 Qt5 在线文档可能重定向到5.15归档，本课代码仍以设备上的 Qt5.12 接口为边界。不了解原生 Transport，可回看第12课。

## 载入位置与生命周期

本课在世界的 `gui` 配置中声明 GUI 插件，注册类型为 `GZ_REGISTER_GUI_PLUGIN`。它不应放进模型、传感器或 visual 的插件位置。相同的 `.so` 文件名并不能替代正确的插件类型和加载层级。

```xml
<world name="lesson30">
  <!-- physics、falling_cube和地面 -->
  <gui>
    <plugin name="teaching_panel" filename="libgazeboteach_l30_gui.so">
      <step_count>100</step_count>
      <display_decimals>3</display_decimals>
    </plugin>
  </gui>
</world>
```

准备程序另外写入实际配置摘要；不要把示意片段复制成缺少物理场景和摘要的完整世界文件。

`GUIPlugin` 同时继承 QWidget 和插件接口。Classic 的实际载入路径会把它设为渲染窗口的子控件、调用 `Load`，然后显示。本课SDK的GUIPlugin及其PluginT基类没有Init/Reset这两个虚方法；不能从其他插件复制相应override。这里讨论的是Load、Qt控件生命期和析构清理，不是上一课VisualPlugin的Init序列。若观察协议保留init_count=0之类的兼容字段，它不表示存在一个等待触发的Init回调。

使用命令行或 `gui.ini` 加载 GUI 插件时，传给 Load 的 SDF 元素可能为空。本课通过个人生成的世界 SDF 提供参数，因此配置校验和文件来源仍是初始化的一部分。

只有服务端就绪不代表面板可用：`after_start` 检查服务端和个人准备结果；打开真实 GUI 后，`after_gui` 再等待面板、控件和统计反馈。无客户端的运行不能标记为 GUI 实验通过。

## Q_OBJECT、槽函数与 moc

源文件把 Qt 类声明与实现分开保存。类使用 `Q_OBJECT`，按钮的 clicked 信号连接到暂停、继续或步进槽函数。槽是普通 C++ 成员函数在 Qt 元对象机制中的一种用途，它不是另起一个物理线程的指令。

`moc` 是 Qt 的元对象代码生成器。准备程序从头文件生成临时 C++ 文件，再将它与实现一起编译进共享库；本例在编译后移除该临时文件，保留实际命令与产物摘要。它不应替代需要编辑的类声明或源文件。工具应由实际Qt开发包定位：本机通过Qt5Core的pkg-config host_bins找到moc，不依赖尚未选择Qt版本的通用qtchooser入口，也不修改宿主全局QT_SELECT。

忘记构建 moc 输出，常会在链接或载入时遇到元对象、vtable 或槽相关符号问题；只把头文件里的宏删掉，不是等价修复。先检查实际 moc 命令、生成文件和参与链接的对象。

不了解 moc，可查看[Qt5 元对象编译器](https://doc.qt.io/qt-5/moc.html)；不了解 C++ 头文件、继承或共享库，可回看第26课。这里无需先学会整个 Qt 应用框架。

## 从点击到物理反馈的完整流程

1. 准备个人参数、SDF 和源码摘要，使用系统 SDK 离线构建 moc 输出、GUI 插件及原生工具。
2. 以暂停状态启动私有服务端，确认真实方块和世界统计已存在。
3. 客户端加载 GUIPlugin；在 GUI 线程创建布局、标签、按钮和刷新定时器。
4. Transport 回调收到原生统计，只在受保护的数据区保存它，不直接调用 QLabel、QPushButton 或布局方法。
5. GUI 线程的定时器读取缓存，更新显示文字和操作状态；自动演示请求也在此进入真实按钮的点击处理路径。
6. 用户点击按钮，槽函数检查当前反馈、是否已有未完成命令以及操作条件。
7. 发布一次原生 WorldControl。暂停和继续等待真实 paused 反馈；步进同时设为暂停并请求 multi_step=N。
8. 面板进入等待状态，禁用会造成重复操作的按钮，继续接收统计；达到真实时间和迭代目标后才确认完成。
9. 通过独立原生查询核对实际世界，再读取方块位姿解释运动。标签变化、按钮回执和世界完成是不同证据。

本课使用 GUI 线程上的定时器消费后台缓存。它与跨线程的 queued signal/slot 都遵守同一原则：后台接收数据，界面对象由所属 GUI 线程操作。不要在消息回调里直接调用控件方法，也不要在 GUI 线程里等待一个阻塞的网络循环。

## 显示频率不等于物理频率

刷新定时器以50毫秒为周期处理界面，但一次刷新可能读到与上次相同的世界统计。它不会因此产生新测量，也不让物理系统每50毫秒只推进一步。

本课固定物理步长为0.001模拟秒。面板同时保留原始模拟时间和用于显示的字符串；`display_decimals` 只决定显示的小数位数。把3位改为1位，会让时间文字变粗略，但不改变真实模拟时钟、物理步长或方块运动。

墙钟时间用于识别等待过久；模拟时间用于计算实验进展。暂停后，窗口仍能刷新和响应按钮，而世界的模拟时间应保持。网络接收或 Qt 刷新有延迟，也不能用本地墙钟补写一条不存在的世界时间。

## 在操作前做预测

默认 `step_count=100`、`display_decimals=3`；步数必须是10..500的整数，显示位数必须是1..6的整数。从刚启动、仍暂停且方块初速度为0的场景开始，预测一次步进的结果：

`delta_t = N * 0.001`

忽略空气阻力与接触，连续时间模型为 `z(t)=2−0.5*9.8*t²`。100步对应0.1秒，预测质心约1.951米；200步对应0.2秒，约1.804米。方块底面低于质心0.2米，首次触地前使用的是自由落体模型。

离散积分会有小误差。以半隐式欧拉的理想离散式说明，`z_N=2−9.8*h²*N*(N+1)/2`，100步约1.95051米、200步约1.80302米；实际结果仍应由 Gazebo 状态验收，而不是把预测值写进界面。

第二次点击时方块已有速度，不能再次把初速度当0。达到地面后，自由落体公式也不再描述后续接触阶段。需要新的从静止释放对照时，重载该项目建立新世界，不把本课步进误当作模型复位。

## 实验操作

进入本课并开始实验后，先阅读 Gazebo 内的控制面板。三个按钮实际显示为 `Pause`、`Resume` 和 `Step N`，分别对应暂停、继续和推进个人配置中的N步。确认状态为paused、模拟时间未推进，再在面板点击一次Step N。观察按钮的等待/完成状态和方块位置，随后对照原生统计。

在操作终端中可检查准备结果和面板反馈：

```sh
python3 lab.py ready-server
python3 lab.py ready-panel
python3 lab.py ready
python3 lab.py predict
```

查看原始数据、自动走按钮槽路径的有限演示及验收：

```sh
python3 lab.py watch
python3 lab.py demo
python3 verify.py
```

自动演示通过排队请求，在 GUI 线程调用同一 QPushButton 点击路径。它能检查槽函数到真实世界的链路，但不能单独证明用户鼠标命中了一个可见按钮。独立图形验收另外对本次窗口发出真实 X11 鼠标事件，并从原生世界状态和实际截图核对结果。

在面板点击“继续”，观察模拟时间增长、方块真正下落并受到地面支持；再点击“暂停”，等面板收到确认。GazeboTeach 顶部按钮、Gazebo 自带工具栏与本课面板都会影响该世界，解释对照时应避免多个控制源同时发令。

## 为什么步进不能自动重发

暂停请求是“使世界处于暂停状态”；步进请求则是“再推进 N 次物理更新”。重复发送步进可能额外推进世界，不能把一次超时当成请求一定没有执行。

面板在发出一次步进后等待实际模拟时间和迭代次数，等待期间不接受第二个相同操作。到达目标才解除 busy；若反馈超时或外部控制破坏边界，应显示错误，先读取实际世界状态，不盲目重放命令来凑成预期值。

离开 GUI 或重开客户端不会把服务端物理倒回。新的面板实例应重新订阅现有世界，而不是在构造函数中私自改写时钟或方块位姿。

只编辑个人练习文件。更改参数或源码后重载项目，重新构建/创建实例；已运行面板不会因文件保存自动替换内存中的值。

第一个对照只把 `step_count` 从100改为200，其余保持。重载后从新世界的暂停初态点击一次，核对实际时间增量、迭代增量和方块位置；不要拿已经连续运行过的方块与从静止释放公式直接比较。

第二个对照只把 `display_decimals` 从3改为1，步数仍100。检查字符串如何舍入，同时查看原始时间字段和实际世界增量。界面显示位数减少不等于物理精度变低。

## 故障诊断

| 现象 | 先检查什么 |
| --- | --- |
| 服务端正常却没有面板 | 是否真的打开gzclient；GUI Overlays是否隐藏；SDF声明和插件类型是否正确 |
| 共享库或元对象符号错误 | moc是否生成并参与编译；Qt/Gazebo开发组件、库路径和ABI是否匹配 |
| 复制Init/Reset override后编译失败 | 本课GUIPlugin接口没有这两个虚方法，按实际SDK声明设计Load与Qt生命期 |
| 标签偶尔落后 | 分开查看原生统计接收、GUI刷新和显示格式，不补造时间 |
| 忙碌状态不解除 | 读取真实世界；查是否超时、断开或被其他控制源改变，不重发步进 |
| 鼠标点了却没有物理变化 | 检查窗口归属、可见/启用状态、槽计数、实际发布及服务端反馈 |
| 保存后仍使用旧参数 | 重载并核对实际配置摘要，而不是反复点击 |
| 关闭面板后世界还在 | 客户端与服务端是不同进程；关闭GUI不等于结束整个实验 |

`View → GUI Overlays` 是 Gazebo 自带的显示开关。显示或隐藏面板不应被解释为世界暂停或插件已经卸载；运行状态应从实际进程与反馈判断。

## 验收与独立挑战

验收需要三层证据：真实可见面板和鼠标交互；原生控制与世界统计；方块实际运动。独立程序对本次 GUI 的按钮使用真实 X11 事件，读取原始统计/实体并保留截图；课程自动演示走 Qt 点击路径，两种检查的结论不互相冒充。

演示会为操作暂时控制暂停状态，正常结束尝试恢复入场暂停状态。已推进的世界时间、物理速度和落点不会回填；发生错误时先按日志检查实际现场。退出、切课或重开只管理本平台创建的进程，不操作其他实验。

挑战：增加“推进指定模拟秒数”的输入框。先定义秒数与整数物理步数的换算、舍入规则、范围和拒绝条件，再复用一次发布/反馈确认机制。另一项挑战是在世界统计长时间没有新消息时，明确显示“反馈陈旧”，而不是让旧时间看起来仍是实时值。

辅助原生工具沿用课程提供的 SDK 退出兼容层，保护范围与实际版本检查见源码和运行日志。它不要求初学者修改系统库，也不应被写进自己的 QWidget 控制算法。GUI 线程和 Transport 线程的分工、可观察世界状态与单次步进语义才是本课的主要工作。
