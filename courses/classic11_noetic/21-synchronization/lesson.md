# 同步、频率与lockstep：先问“每哪一秒”

相机配置20 Hz，观察者每真实秒却只收到10张图，是少拍了一半，还是整个仿真以半速运行？相机和IMU的时间戳一样，就能说它们像现实硬件一样同步曝光、同步采样吗？本课把这些问题拆成可以实际测量的时间与频率，再用Classic的lockstep（锁步）模式比较物理推进和传感器更新。

本课研究真实消息的时间标签、到达顺序和窗口统计。几何或频率公式用于解释观测，不靠补帧、重复发送、修改时间戳或等待一个恰好好看的窗口来制造目标频率。运行较慢本身也是有效结果；要先说明慢的是哪一条时间轴。

## 项目：同一试架的相机与IMU记录

主实验以完整`--lockstep`模式启动一个world。sync_rig是禁用重力、关闭速度衰减的动态试架；IMU在质心，相机安装在局部z=0.2 m。它们在本课保持静止，避免把运动模型变化混进时间实验。相机分辨率128×96、默认20 Hz，原生IMU目标100 Hz；物理步长默认1 ms，real_time_update_rate=1000，使名义RTF上限保持1。

真正的原生相机图像、IMU、WorldStats和PerformanceMetrics进入SDK观察程序；课程适配管道再将这些实际事件转发为ROS `/lesson21/events`，由真实订阅回调接收。另有服务器内轻量只读回调，记录相机成功原生Update次数与对应LastMeasurementTime，并随metadata发布一致快照。生产端更新、消息被观察到、ROS收到，是需要分开测量的层次。该管道是本课准备的适配程序，不是Gazebo标准ROS相机/IMU包装器。

```text
真实相机成功Update → 只读计数/LastMeasurementTime → metadata快照
真实相机/IMU消息 + 世界统计/内置性能指标 + metadata
  → 原生Gazebo Transport消息
  → SDK观察：原生protobuf、图像base64、CLOCK_MONOTONIC
  → Python真实发布ROS事件
  → 真实ROS订阅回调记录收到时刻
  → 窗口频率、暂停/步进、配对和独立模式比较
```

base64只是把真正图像字节编码进SDK输出文本，不生成图像、不补帧。Python收到后将像素转存为带SHA256的实际.rgb文件，ROS事件转发原生字段与binary_storage存储引用；它不是通过ROS Image主题再传一遍全部像素。小分辨率用于把注意力放在时序和管道上；这不是机器人全部图像吞吐的基准。画面来自真实渲染，IMU来自真实原生传感器；成功更新率、标签密度和接收率分别计算。

## 四种容易被写成“time”的东西

| 名称 | 本课含义 | 能用它回答什么 |
| --- | --- | --- |
| simulation time，仿真时间 | 某个Gazebo world的模拟时间 | 模拟世界前进了多少秒 |
| wall elapsed，观察者实际耗时 | 使用单调时钟计量的真实经过时间 | 等待实验花了多少真实时间 |
| native measurement stamp，原生测量时间标签 | 传感器原生消息附带的仿真时间 | 该消息在生产者时间线上标在何处 |
| receive time，接收时间 | 桥/观察者收到回调时记录的时间 | 消息何时到达这一层观察者 |

**单调时钟（monotonic clock）**适合计算耗时：它不因修改系统日历时间而倒退。它不是当前北京时间，也不是某个world的仿真时间。若不知道Python计时接口，可以看[Python time.monotonic说明](https://docs.python.org/3/library/time.html#time.monotonic)；本平台使用的接口在Python 3.8中已提供。

原生测量stamp也不是现实传感器曝光起止时刻或UTC时间。它首先是这条仿真生产链路附加的标签；要知道标签来自scene时间、link状态时间还是某个回调，必须查接口定义。接收时间则还混入线程调度、消息传输、队列和观察者处理，不能拿到达顺序直接代替测量顺序。

这四种含义不代表四个独立物理时钟：原生stamp通常使用所属world的模拟时间基准，本课观察/发送/接收字段则使用同一主机的单调时钟，分别标记不同事件。必须先看字段来源，再做相减或配对。

本课讨论的“同步”应说明层次：可以是物理与渲染调度同步、消息按时间标签配对，或硬件采样触发同步。它们有关联，但不是同一个承诺。

## 配置Hz、观测标签密度与墙钟接收Hz

**Hz（赫兹）**表示每秒次数；关键是这里的一秒属于哪条时间轴。SDF的sensor update_rate描述目标仿真采样频率，不是无条件保证每真实秒收到相同条数。图像尺寸、物理步长、算力、调度和订阅链路都会影响观察结果。

先看主窗口：同一路首次观测的不同原生标签按观测顺序严格递增，留下N个标签，第一/最后为s0、s1，对应这两个事件的接收单调时钟为w0、w1，则：

```text
f_sim  = (N−1) / (s1−s0)    每仿真秒的已观察到的不同样本数
f_wall = (N−1) / (w1−w0)    每真实秒的已观察到的不同样本数
ratio_span = (s1−s0) / (w1−w0)  同事件标签/接收跨度比
同一组样本端点下：f_wall = f_sim × ratio_span
```

这里用N−1，因为N个标签之间只有N−1段时间间隔。f_sim是这份观察记录的标签覆盖密度；在主窗口严格递增的前提下，用它检查观测到的采样节奏。它仍不证明生产者每次内部更新都被完整记录。只数“收到了20条”，却不记录实际窗口长度，不能得到可信的20 Hz。重复stamp、时间倒退、间隔分布和原始消息数量也应单列，不能先丢掉异常再只给一个平均值。

**RTF（real-time factor，实时因子）**表示模拟秒与实际秒之比。RTF≈1是接近实时；0.5表示一个模拟秒大约要两个实际秒；大于1表示这一窗口的模拟推进快于实际时间。它没有单位，不是“CPU利用率”或某个传感器的Hz。

举一个计算例子：若51个不同样本跨1仿真秒、2实际秒，f_sim=50 Hz、f_wall=25 Hz、样本跨度比为0.5。若同窗WorldStats的RTF也接近0.5，就支持“仿真约半速”的解释；样本跨度比本身还可能受接收时延变化影响。这组数字只用来说明计算，实际实验请读自己的报告。

WorldStats或内置PerformanceMetrics计算的RTF使用世界时间与各自窗口，不必与以上样本跨度比完全相等。比较前先核对窗口，不能把不同窗口的几个数字强行相乘，再断言消息必然丢失。

## child标签回退时，分开看接收事件和标签覆盖

解除实时限速的独立比较中，实际可能观察到同一source的标签相对观测顺序回退：后收到的事件，native stamp比前一个小。这个现象不能仅凭当前记录定位到生产者调度、传输、队列或观察线程中的某一层，也不能直接叫作“网络包重排”。重复时间标签事件同样不自动等于重复曝光或重复数据包。

本课保留采样窗口内raw trace的观测顺序，另建一个**去重后升序的标签统计视图**。两者用途分开：

| 统计 | 分子和分母 | 能说明什么 |
| --- | --- | --- |
| 原始接收率 | (接收事件数−1)/(最大receipt−最小receipt) | 这条路径每实际秒观察到多少事件，包含重复标签 |
| 不同标签覆盖密度 | (unique标签数−1)/(最大label−最小label) | 已观察标签集合在模拟时间范围内的密度 |
| unique事件接收率 | (unique标签数−1)/(各标签首次观测事件的receipt范围) | 去重代表事件在实际时间上的接收密度 |
| 回退/重复诊断 | 相邻raw事件的标签比较、重复标签数量 | 标签与观测顺序是否一致，最大回退多大 |

报告兼容字段sim_rate_hz在child中指第二行的**观察标签覆盖密度**，不是已证明完整的生产者capture Hz。排序只服务统计和最近邻查询，不改变原trace，不改标签，不将排序后的第i个stamp重新配给原第i个receipt。它没有“修复同步”或找回缺失测量。

因此不能将child原始接收率和标签密度直接套进前面的同事件端点等式；它们可能使用不同分子和不同事件边界。世界推进速度另看WorldStats的RTF。主窗口仍要求首次观测的不同标签按原顺序严格递增，并保持相机/IMU门限；独立child允许把回退作为需要报告的真实现象。

## 再看生产端：成功Update与消息交付是两层

只看到接收标签较稀，不能判断相机内部到底完成了多少次更新。本课在服务器内通过Camera Sensor的ConnectUpdated注册只读回调：Sensor::Update只有在UpdateImpl成功后才触发它；相机这条成功路径已完成rendered检查和PostRender。因此计数名称是**成功原生sensor Update事件**，不是硬件曝光次数，也不保证对应Image消息已交付观察器或ROS订阅者。

回调将event_count与当次LastMeasurementTime一起存成一致快照，metadata再发布这些累积值。窗口首末快照为(C0,t0)、(C1,t1)，则：

```text
successful_update_rate = (C1−C0) / (t1−t0)
```

例如计数从100到140、对应测量时间从5到7仿真秒，窗口有40次新成功更新，率为20 Hz；这里**不能再减1**。这只是公式示例，不是要求机器给出指定计数。仪表可能晚于world启动才挂接，所以只保证挂接后窗口增量，不宣称从world起点完整计数。

这个t来自成功更新回调读到的Camera LastMeasurementTime；它与原生ImageStamped.time取值的代码阶段不同，不能把两者无条件当作同一字段。元数据快照也只是仪表状态，不是又多拍了一帧。

独立lockstep_on的目标节奏以这条真实成功Update计数、至少1仿真秒的测量时间窗口验证，相对配置误差要求不超过2%，该producer窗口测量标签的重复/回退增量均须为0。child的消息接收率、unique标签覆盖密度、重复/回退继续原样报告，作为交付观察诊断，不再拿它们替代完整更新证据。主实验既有的相机/IMU观测标签单调与20/100 Hz门限保持。

## 暂停会停止哪条时间轴

暂停物理后，正常的仿真时间与新测量时间不再持续推进，观察者的实际计时仍前进。恢复运行后，模拟时间接着前进；按实际时间设置的超时不能依赖已经暂停的仿真时钟，否则可能永远等不到超时。

Classic的WorldStats.real_time还有一个容易漏掉的细节：该值扣除了world累计暂停时间，并在暂停时固定。它不是包含暂停等待的观察者wall elapsed。因此读WorldStats时要把sim_time、real_time、pause_time、paused分开；不能仅凭字段名real_time就当作当前操作总共花费的真实时间。

ROS环境可以由`/clock`传递仿真时间，`/use_sim_time`让ROS时间采用该时钟；平台已准备本课环境，不要求先手工配置ROS时钟。其消息本身只是[Clock定义](https://github.com/ros/ros_comm_msgs/blob/noetic-devel/rosgraph_msgs/msg/Clock.msg)中的一个时间值，不是传感器帧号。ROS时间的集中讲解在后续课程展开。

## 同样的stamp不等于同样的现实采样动作

两个消息带同一个仿真时间数字，只能先说它们具有相同时间标签。相机渲染、IMU读取刚体状态和ROS包装可能位于不同回调阶段；现实相机的曝光、滚动快门、IMU积分区间与硬件触发也不是这个标签自动模拟出来的。

例如某条较晚标记的IMU数据先到、较早标记的图像稍后到，是两条处理路径时延不同的正常可能性；不表示它们的测量时间必须倒过来。跨主题到达顺序没有全局采样排序保证。同一路的原始顺序仍应保留，出现stamp回退要记录来源、上下文和幅度；不能无条件排序后掩盖现象，也不能未经额外证据就归因于某一网络层。

按时间配对时要先声明策略：exact matching只接收相同stamp；nearest matching寻找邻近标签，但必须记录差值与容许范围。nearest不等于同时采样，不能把原来的两个stamp改成一个共同数字来假装exact。若画面运动快，即使时间差很小，也可能带来明显空间误差。

## Classic lockstep实际做什么

正常模式允许物理推进与图像渲染等工作异步进行。若相机工作赶不上，实际仿真采样率可能偏离配置；算力充足时也可能已经达到目标，不能预先规定“非lockstep一定漏帧”。

实际观察到标签覆盖较稀时，还要联合读接收率、回退/重复与服务器元数据；仅凭覆盖密度不能定位到底是哪一层没有完成更新或没有交付到本观察器。

使用服务器启动参数`--lockstep`后，Classic建立严格传感器调度和物理/渲染等待关系：该完成的图像更新未跟上时，世界推进会等待它。这样有助于按仿真时间遵守目标传感器节奏，代价可能是更多实际耗时或更低RTF，而不是凭空增加GPU/CPU算力。官方机制说明见[Classic物理与传感器lockstep教程](https://classic.gazebosim.org/tutorials?tut=lockstep_physics_sensors)。

本课比较的是完整服务器模式：用/不用`--lockstep`分别启动新world，再比较实际数据。它涉及服务器初始化的姿态同步回调、主循环分支和传感器加载时缓存的strict-rate设置，不能只在运行中翻一个全局布尔值，就宣称完成了等价切换。

lockstep也不承诺所有传感器在每个物理步都采一帧，不把不同配置Hz变成相同Hz，也不会自动消除ROS队列延迟、硬件曝光模型或所有数值误差。不要照抄官方示例机器的RTF或500 fps作为自己的验收结论。

## 物理步长给采样时间铺了一张网格

ODE在本课使用固定物理步长h。若h=0.001 s，物理状态沿1 ms网格更新；若目标频率为250 Hz，周期T=0.004 s正好是4步。目标400 Hz的T=0.0025 s则不是1 ms的整数倍，不能要求每个相邻stamp都严格相差2.5 ms。

非整数关系时，可能出现不同间隔或平均频率偏差，具体取决于传感器类别、补偿机制和运行模式；不能事先规定所有传感器都交替2/3 ms，或都降成某个固定Hz。即使T/h为整数，也只是使该周期可被网格表达，不保证算力、线程和消息链路一定跟得上。

减小h能细化网格，但同一模拟秒需要更多物理迭代，会改变计算成本，也可能影响数值精度；它不等于只给相机“加帧率”。相关官方说明见[Classic Performance metrics中的步长讨论](https://classic.gazebosim.org/tutorials?tut=performance_metrics)。

## 不同world的数字不能直接拼成一条时间轴

每次独立服务器/world运行都有自己的模拟起点、暂停、推进速度和迭代计数。两次运行都出现stamp=2 s，只说明它们各自来到第二个模拟秒，不表示同一现实瞬间。比较实验应比较各自的间隔、频率和局部窗口，而不是把绝对stamp相等当作跨world同步。

运行有/无lockstep的独立实验时，应保留模式、world标识、配置和报告路径。平台的隔离实例与观察记录帮助区分来源；不要把另一个实验的`/clock`或相机主题混入本次窗口。

## 实验顺序与单变量

先在主实验记录连续2仿真秒的相机/IMU事件、接收时刻和世界统计；然后暂停一段真实时间，检查实际耗时增长而模拟时间不连续推进；再做真正的单个物理步和多个物理步，对照迭代计数与Δsim=N×h。一步不一定让相机或IMU各更新一帧，传感器仍按自己的目标周期调度。

lockstep比较则先暂停主world，依次启动两个独立短生命周期gzserver。两者使用相同临时场景副本、相同传感器参数与资源，副本共同把real_time_update_rate设为0以解除实时限速；两次服务器命令的模式差别是有/无`--lockstep`。这两个child使用私有Gazebo Master与Ignition partition，不创建第二套ROS或第二个GUI，完成后只清理本课创建的子进程。

主实验保持RTF上限1，两个child共同解除限速，因此**应先比较两个child之间的差异**，不能把主world与某个child的不同RTF全部归因于lockstep。解除限速也不保证实际RTF一定大于1。比较记录有限窗口，并记录实际strict标志、传感器rate和物理步长，不只保存一个命令行开关当作运行证据。

保存参数的两个单变量为：

| 实验因素 | 支持值 | 需要保持的其他条件 |
| --- | --- | --- |
| 相机目标频率 | 10或20 Hz | 分辨率、IMU100 Hz、物理步长不变 |
| 物理步长 | 0.001或0.002 s | real_time_update_rate联动为1000或500，保持名义RTF上限1 |

步长实验改变的是一个实验因素；为了保持相同实时上限，限速参数需要联动，不是声称SDF只改一个标签。保存后重载，再采集新窗口。不要同时改相机Hz和步长后，把所有差异只解释成某一个因素。

## 操作入口与报告

请使用平台打开的本课操作终端：

```sh
python3 lab.py observe --seconds 2
python3 lab.py compare
python3 verify.py
```

这里observe/probe的`--seconds`表示最低**仿真时间跨度**，支持0.5至5秒，与前面某些课程按墙钟限时的observe不同；实际耗时另列，并有有限墙钟超时。observe会临时恢复运行，经过真实ROS发布/订阅链路采集，最后恢复进入命令时的暂停状态。`/lesson21/events`只在相应适配命令存活时发布，不能在没有运行观察程序时将空主题误诊为相机损坏。

`python3 lab.py probe --seconds 2`只走原生SDK观察，不经ROS事件转发，也不主动改变暂停状态；暂停时先点“继续”，才能形成新样本窗口。`lab.py ready`用于启动就绪检查。probe与observe各自的时间路径不同，不能拿两个命令的不同结果就断言ROS一定改变了原生采样。

compare先暂停主world，串行创建off/on两个独立实例，最后清理本课子进程并恢复主world原暂停状态。每个child须先看到五种来源，再满足至少2实际秒、1仿真秒标签覆盖，以及至少8个不同相机/20个不同IMU标签；另须形成至少1模拟秒的相机成功Update计数窗口。这些是最低条件，并不保证off/on的实际窗口长度完全相同。比较时分开读成功Update率、原始接收率与标签覆盖密度，核对各层重复/回退诊断，不能只比条数或把标签密度称作生产者完整采样率。

完整verify依次运行continuous、pause_hold、single_step、multi_step与两个child比较，平台墙钟超时为180秒。连续主窗口至少2仿真秒；暂停检查包含至少0.35实际秒；单步为1次物理迭代，多步固定推进0.1仿真秒，即1 ms步长下100步、2 ms步长下50步。它会改变暂停状态并让时间前进，结束恢复原暂停状态与本课创建的观察进程；已经流逝的仿真时间不会倒回。

验证将原生WorldStats的sim_time/iterations与通过ROS服务查询到的Gazebo世界时间对照。这个服务查询不是本课另一次对`/clock`的订阅，也不冒称验证了所有ROS节点的时间行为。

报告默认存于会话目录：observe/probe/compare使用timing-唯一编号/report.json，完整verify使用synchronization-唯一编号/verify.json；终端打印trace_path。可用`--report PATH`指定JSON位置，图像原字节与运行日志仍放在该次生成的会话目录，迁移报告时应连同引用文件一起保留。

保存单变量可用：

```sh
python3 lab.py config --camera-hz 10
python3 lab.py config --step-ms 2
```

这是两个分别执行的实验入口，每次只做一项、保存后重载；先把该参数改回默认20 Hz或1 ms，再重载恢复基线，才做另一项。配置编辑器直接改个人world.sdf，步长与限速联动，其他几何/传感器契约由预检固定。保存但尚未重载的输入会被观察/验收拒绝。

## 按时间来源诊断

| 现象 | 先检查的证据 |
| --- | --- |
| 配置20 Hz，实际每秒只收10条 | 看原生stamp跨度、接收单调时钟跨度与RTF，区分仿真半速和采样未跟上 |
| 相机与IMU到达顺序交错 | 分别保留两路原生stamp和接收顺序，不把跨主题到达顺序当作采样排序 |
| 两路没有相同stamp | 看采样率、步长与相位；nearest需明确容差，不改写原始stamp |
| 暂停后没有新图像/IMU | 查看paused与sim_time；实际计时继续不代表需要继续采样 |
| 暂停时WorldStats仍出现 | 它是状态通知，检查sim_time是否真的变化，不能把每条通知算成新物理采样 |
| 真正单步后还没有新图像 | 相机周期可能需要很多物理步，先核对Δsim和迭代差 |
| 重置后stamp变小 | 建立新的world/时钟窗口，不跨重置计算负时长Hz |
| child同一路标签相对观测顺序回退 | 保留raw顺序，读回退数/幅度与标签密度视图；当前证据不能定位为网络包重排 |
| off/on标签密度和接收率差异很小 | 先确认实际strict标志与同一场景配置；当前负载可能两者都跟得上 |
| lockstep下RTF较低 | 看实际仿真Hz是否保持目标、真实耗时是否增加，别把等待等同于数据错误 |
| 内置fps与ROS接收Hz不同 | 它们属于渲染器和订阅路径的不同统计，先对齐时间源与窗口 |
| 早期PerformanceMetrics有异常数值 | 保留原始诊断，使用明确稳态窗口，不挑一个瞬时值充当实验结果 |
| 成功Update率达标，接收标签密度较低 | 两者属于不同观测层；保留counter快照及raw交付诊断，不能直接定位网络或宣称曝光完整送达 |
| rostopic看不到/lesson21/events | 运行observe等ROS适配命令；probe是纯原生路径，不发布该主题 |

先判断来源和时钟，再判断错误；单独一个“Hz”或“FPS”标签不够定位整条链路。课程窗口包含观察与转发开销，实际结果也会受当前机器负载影响，报告应记录运行配置。

## 预测、记录、独立挑战

先预测再运行，每个实验至少记录配置Hz、原始事件数/unique数/重复标签数、标签跨度、接收耗时、标签密度、原始接收率与RTF来源。child再记成功Update计数首末快照、计数差/测量时间跨度，以及交付标签回退数和最大幅度。为配对另记原始两个stamp、代表事件序号、时间差与未匹配数量；为步进记初末sim_time、iterations、请求步数和h。

1. **同频率、不同真实耗时**：相机参数不变，比较主world与同配置的另一次记录。若实际每秒收到的条数不同，判断差异是否能由各自的时间跨度解释，不用“机器卡了”代替数据。
2. **改相机频率**：仅将20 Hz改为10 Hz，重载后预测周期、相同仿真窗口的样本数和相机/IMU配对机会；核对实际报告，不要求原生起始相位完全相同。
3. **改步长**：仅将1 ms改为2 ms并保持实时上限，预测一步和N步的Δsim、20 Hz相机一周期相当于多少步。用实际迭代计数和时间差检查，别按收到的图像条数反推物理步数。
4. **比较lockstep**：只比较两个相同临时场景child，写清模式、窗口、标签密度和接收率。检查是否出现标签回退，并说明当前数据不能定位的因果层。即使差异很小，也报告原值，不通过增加假延迟制造“明显效果”。
5. **配对策略**：对同一份原始时间序列比较exact与nearest结果，声明最近邻容差及未匹配样本。解释“配对成功”能证明什么，以及它没有模拟的硬件触发或曝光过程。

最后写三句带证据的实验结论：一句说明仿真采样节奏，一句说明实际耗时/RTF，一句说明两路配对边界。每句都带上时间源和窗口；这样另一位学员才能用报告复核你的结论。

## 原生辅助工具的退出流程

本课通信工具先核对编译SDK与实际Transport动态库均为Classic 11.15.1，并检查兼容层需要的符号；不匹配时在Transport初始化前报错。主线程随后持有一个未连接的Connection，再初始化通信。这个持有者保证异步回调不会成为共享IOManager的最后一个所有者。通信结束或出现异常时，先执行Transport fini，再在主线程调用公开IOManager.Stop并等待IO线程结束，最后释放订阅、发布器、节点和持有者；回调使用的对象一直保留到这两个停止屏障之后。

这段流程只负责独立辅助进程的资源寿命，插件宿主中不执行全局Transport退出。原有命令参数、测量输出与每次控制只发布一次的规则保持；它不写入预测姿态、力或轨迹。编译缓存包含本课变更的C++源码与SDK/链接参数，保存源码后须重新准备或重载。设置`GAZEBOTEACH_IO_DIAGNOSTICS=1`可在标准错误流保留实际IO join证据，不混入实验数据输出。
