# SensorPlugin：把真实测距变成可解释的接近判断

本课给一只真实的 CPU 激光传感器编写 `SensorPlugin`：读取三束原生测距，求最近有效距离，进行指数移动平均，再按阈值输出接近、未接近或未知。目标方块真正改变位置，测量由 Gazebo 的射线与碰撞几何产生；插件只处理已有测量，不代替传感器生成距离。

你会同时观察原生 `LaserScanStamped` 和插件的自定义消息。前者回答传感器实际量到了什么，后者回答这段程序怎样处理输入。两路都来自同一个实验，但自定义结果需要用原始测量独立核对，不能拿插件自己报告的“正确”作为唯一证据。本课使用 Gazebo Classic 11，不依赖 ROS。

## 从模型和世界，转向传感器

第26课的 ModelPlugin 接到模型，第27课的 WorldPlugin 接到世界。本课的 `SensorPlugin::Load` 接到 `sensors::SensorPtr` 和插件配置；它的更新事件是传感器完成测量后的 `ConnectUpdated`，不应照搬每个物理步都施力的更新循环。

本例把父对象检查并转换为 `RaySensor`，因为读取激光量程和距离数组需要它的具体接口。`dynamic_pointer_cast` 的失败需要明确报错；声明在相机或 IMU 下的插件，即使库能被找到，也不会自动拥有激光接口。注册宏和 SDF 声明位置同样要匹配传感器插件的类型。

不了解 C++ 指针、继承或动态类型转换，可先回看第26课，并查阅[传感器插件 API](https://osrf-distributions.s3.amazonaws.com/gazebo/api/11.0.0/classgazebo_1_1SensorPlugin.html)。不了解一帧激光的角度与数组关系，可回看第15课，再查阅[Classic RaySensor API](https://osrf-distributions.s3.amazonaws.com/gazebo/api/11.0.0/classgazebo_1_1sensors_1_1RaySensor.html)。

## 场景与先做的预测

固定扫描器位于高度0.4 m，三束光线朝向世界 +x，水平角为 −0.1、0、+0.1 rad，量程0.1～6 m，名义更新率20 Hz。目标方块边长0.4 m、无旋转；中心 x=1.4 m 时，正前方表面距扫描器约1.2 m。

若方块仍覆盖三条射线，则斜束到同一平面的距离为 `1.2/cos(0.1)`，中间束为1.2 m，因此最近值为1.2 m。把中心移至0.8 m时，最近值约0.6 m；移至3.2 m时约3 m；移出量程后应检查真实无回波表示，不能把无效值解释成“确定没有障碍”。

默认阈值0.9 m、EMA系数0.35。开始前写下：三个有回波位置各应给出什么最近距离；从远处突然移近时，滤波值会立即等于新距离还是逐帧趋近；完全无回波时，系统应如何表达不知道。

## 声明位置、对象与生命周期

传感器属于 link；处理其数据的插件应放在对应 `sensor` 元素内部。下列片段省略了扫描参数和准备阶段写入的摘要：

```xml
<model name="scanner">
  <link name="link">
    <sensor name="proximity" type="ray">
      <update_rate>20</update_rate>
      <!-- ray / scan / range 定义三束光线 -->
      <plugin name="proximity_filter"
              filename="libgazeboteach_l28_sensor.so">
        <threshold_m>0.9</threshold_m>
        <alpha>0.35</alpha>
      </plugin>
    </sensor>
  </link>
</model>
```

世界名是 `lesson28`，世界内传感器作用域为 `scanner::link::proximity`；完整名称还可包含世界前缀。父传感器的类型、SDF中的插件实例名、C++类名和共享库名分别承担不同职责。课程提供的观测工具负责原生消息收发，学习重点是传感器插件怎样处理一帧真实数据。

| 接口或对象 | 本课中的含义 |
| --- | --- |
| SensorPlugin / GZ_REGISTER_SENSOR_PLUGIN | 传感器插件基类及注册入口 |
| SensorPtr / RaySensorPtr | 通用父传感器与经检查的具体激光接口 |
| Load | 取得传感器、读取参数、建立通信及更新连接 |
| Init | 本次插件加载之后的初始化回调 |
| ConnectUpdated | 在传感器完成成功更新后调用处理函数 |
| Ranges / RangeMin / RangeMax | 真实距离数组及有效量程边界 |
| LastMeasurementTime | 本次实际测量对应的模拟时间 |
| ConnectionPtr | 保存事件连接，避免局部变量结束后失去更新订阅 |

`SensorPlugin` 基类声明了 `Reset`，不代表每种世界复位都会自动调用它。本课所针对的 Classic 11 路径会在加载传感器插件时调用 Load、Init；传感器的采样时钟复位和世界插件的 Reset 调度不同。应分别观察 `load_count`、`init_count`、`reset_count` 与测量时间，不能依据函数名字猜测实际调用。

本课插件遇到真实测量时间回退时，新建处理 epoch 并清除 EMA 历史。epoch 表示一段连续的处理时间，不是伪造的传感器时间。原时间戳照常保留；Load/Init不因此重跑，是否调用过Reset也另有计数。完整重载则创建新的传感器与插件实例。

`SetActive(true)` 可以显式激活父传感器。本例 RaySensor 也会在原生 scan 有订阅者时保持活动，所以仅设置 false 并不能保证“有人观察原生扫描时仍停止测量”。`active`、是否有订阅、世界暂停与传感器采样率是四个不同问题，不要把任何一个布尔值当作整条数据链的状态。

传感器回调可能由传感器线程执行，不是桌面界面的按钮回调。代码先读取已完成测量的数组和时间，再在自己的状态锁内处理递推；查询回调只复制缓存，不持锁访问传感器。事件连接保存为成员，回调使用弱传感器引用和共享状态，销毁时先停止接收再释放资源，避免局部连接失效、悬空对象或循环引用。在测量回调中长时间等待终端、绘图或网络，会阻塞数据处理，不适合作为初始写法。

## 两条数据链与时间标签

```text
目标的真实碰撞几何
  → CPU RaySensor 射线测量
  ├→ 原生 LaserScanStamped：角度、范围数组、原生测量时间
  └→ ConnectUpdated 回调
       → 最近有效距离 → EMA状态 → 阈值判断
       → 自定义 Any.STRING JSON
```

原生主题为 `~/scanner/link/proximity/scan`，自定义主题为 `~/sensor_plugin/state`；在本课私有世界中分别展开为 `/gazebo/lesson28/...`。`~` 使用当前节点的世界名称空间，不是家目录。自定义消息用 `gazebo.msgs.Any` 的 STRING载荷承载 JSON，并没有把 `Any` 变成新的传感器类型。

| 字段 | 怎样解释 |
| --- | --- |
| source_time_ns / source_time_s | 实际测量时间；纳秒以字符串保留，秒值便于阅读 |
| raw_ranges_m / raw_kinds | 本帧读到的距离及有限、无穷或NaN的分类 |
| valid_count / nearest_m | 有效束数及本帧最近有效值 |
| previous_filtered_m / filtered_m | 递推前、后的处理状态 |
| alarm_state | near：滤波值≤阈值；clear：有效滤波值>阈值；unknown：本帧无有效回波 |
| callback_count / epoch / rewind_count | 实际回调、处理时间段和测量时间回退计数 |
| load_count / init_count / reset_count | 不同生命周期回调各自的计数 |

JSON不采用非标准的无穷数值：自定义数组中的非有限回波用 null，并另存分类。原生 protobuf 仍保留它自己的真实表示，null不是声称传感器原本测出了一个JSON空值。完全无有效回波时 `nearest_m` 与 `filtered_m` 均为null，`alarm_state` 为unknown。

RPC `gazeboteach_sensor_snapshot` 返回最后一帧已处理数据及查询关联信息。新查询可以获得新回执，但暂停时其测量时间仍可能不变；这不是新采样。SDK工具另外记录的接收耗时属于维护端时钟，也不能代替测量时间计算传感器频率。

不了解名称空间、消息类型和请求响应，可回看第12课，并查阅[Classic Transport Node API](https://osrf-distributions.s3.amazonaws.com/gazebo/api/11.0.0/classgazebo_1_1transport_1_1Node.html)。不了解JSON，可查阅[JSON格式说明](https://www.json.org/json-en.html)；这里只需认识数字、字符串、数组和null，不需要先学习网络服务。

## 最近有效值与EMA的处理顺序

个人参数文件为：

```json
{"threshold_m": 0.9, "alpha": 0.35}
```

本课接受有限阈值0.2～4 m、alpha为0.05～1；布尔值、额外键和非有限数值会被拒绝。范围限制用于保持这个小项目可解释，并不是宣称所有滤波应用都应采用相同参数区间。

每一帧先检查真实数组，再更新处理状态：

1. 只接纳有限且落在有效范围 `[RangeMin, RangeMax)` 内的回波。量程上限本身不当作确定的障碍距离。
2. 有有效回波时取最小值 `d_k`，不把未命中束的无穷值带入递推。
3. 没有已有有效历史时，用 `y_k=d_k` 初始化；否则使用下式。
4. 以滤波后的距离和阈值比较，`y_k <= threshold_m` 表示接近。
5. 本帧完全无有效回波时，清除滤波历史并输出unknown；重新看到有效回波后，从当前真实距离重新初始化。

验收器也按有效段检查状态衔接：仅在同一epoch内连续有效时，才要求本帧previous等于前帧filtered；本帧无效时nearest、previous和filtered均须为null，前帧无效后的首个有效帧则重新初始化，不把unknown硬接回先前的有效历史。

```text
y_k = alpha*d_k + (1−alpha)*y_(k−1)
```

EMA是指数移动平均：只保存上一个滤波状态，不保存固定长度的全部窗口。alpha越大，本帧权重越大，变化跟得更快；alpha越小，历史影响持续更久。它不能凭空增加测量精度，也不能恢复量程外目标的位置。本课不加噪声，正是为了先看清算法本身带来的延迟；给无噪声阶跃做滤波不会自动让所有任务更好。

若滤波已稳定在1.2 m，目标突然移到0.6 m，理论上连续有效采样为：

| 近处采样序号 | alpha=.35 的滤波值(m) | 与阈值.9比较 |
| --- | --- | --- |
| 第1帧 | .99 | 尚未接近 |
| 第2帧 | .8535 | 接近 |
| 第3帧 | .764775 | 接近 |

alpha=.7时，第一帧即为.78 m。表中的序号从真正测到新位置的第一帧开始，不能从“移动命令刚返回”开始数；若此前滤波历史不是1.2 m，必须使用实际 `previous_filtered_m` 重新计算。

不了解递推和滤波，可先看[指数平滑的基础说明](https://www.itl.nist.gov/div898/handbook/pmc/section4/pmc431.htm)。本课的EMA按有效采样次数更新，未把不规则时间间隔自动换成时间常数；若将来改采样率，需要重新评估实际响应时间。

## 文件与准备过程

| 文件 | 用途 |
| --- | --- |
| world.sdf | 固定扫描器、目标碰撞几何、光照和传感器声明 |

| parameters.json | 本课两个可修改的处理参数 |
| prepare.py / config.py | 参数校验、个人SDF、离线构建及输入摘要 |
| lab.py | 就绪、预测、实际目标移动和有限实验 |
| verify.py | 运行真实验收并输出结果 |

点击“开始实验”后，平台准备个人副本，依据实际SDK、编译器及源文件建立缓存键，按键加锁并离线编译。插件共享库放入个人构建路径，SDF加载自己的库；原始模板不会被个人实验改动。缓存锁和临时输出的原子安装避免两个练习同时覆盖正在加载的产物。

修改参数、SDF或C++后需要“重载项目”，让构建、Load及已缓存的配置同步。保存文件不会自动修改已经运行的C++对象。就绪检查会核对输入与实际插件的源/配置摘要；未重载而输入已变时明确拒绝，避免把旧算法结果当成新参数的效果。

观测客户端沿用第27课已验证的Classic SDK退出兼容流程：先检查SDK、运行库全版本与兼容符号，再由主线程持有连接寿命；正常通信结束后，先结束Transport运行，再明确停止并等待异步IO，最后释放订阅及节点。这个辅助层针对已验证的Classic11.15.1，依赖符号或版本不符时明确报错，不修改主机SDK。初学者不需要为本课修改这个辅助层，SensorPlugin教学本体也不使用其私有ABI。

## 按顺序做实验

开始实验后，在本课操作终端执行；终端已位于个人练习目录，环境使用本课私有Master。

```sh
python3 lab.py ready
python3 lab.py predict
python3 lab.py demo
```

先确认真正载入了本课插件，再看预测，最后做完整有限演示。观察目标在Gazebo中的真实位置，并比较同一阶段的原生扫描、插件最近值、旧滤波值、新滤波值和判断结果。演示不是在终端中打印预先写好的“0.6 m”，应能沿原生消息追溯距离。

也可逐个位置操作。`home`、`near`、`far`、`noecho` 都会先暂停并修改目标的真实位姿，查询实际应用结果；移动本身不会推进新的测量。下面只对near阶段示范一次完整观察：

```sh
python3 lab.py near
python3 lab.py resume
python3 lab.py watch --seconds 2
python3 lab.py pause
```

将第一条命令换成home、far或noecho，再重复继续、观察和暂停，比较各阶段。每次移动后再观察多帧，区分模型操作完成、下一帧实际测到，以及EMA逐步变化。特别看far阶段：前表面x=3 m，斜束横向偏移约±.301 m，已超过方块半宽.2 m，因此只有中心束应命中。三个数组元素不代表三个都有效。`watch`只订阅并保留数据，不自行继续世界。

暂停后比较最后测量时间与回调计数，再试真实步进：

```sh
python3 lab.py pause
python3 lab.py step --steps 100
python3 lab.py resume
```

100个1ms物理步是0.1模拟秒，不能因此断言必有100个传感器回调。20Hz名义周期为0.05模拟秒，实际采样还受传感器线程调度影响；应读出本次源时间与回调，而不是由物理步数补造采样。暂停边界前已排队的测量回调可能稍后完成，但它的测量标签不应超出冻结的世界时间；不要把这类完成误判成世界又自行推进。纯物理暂停也不会把最后一帧缓存擦掉。

## 单变量修改与独立挑战

先保存原文件，每次只改一项并重载，再运行相同实验。

| 修改 | 预测与观察 |
| --- | --- |
| 仅threshold_m由.9改为1.3 | 同一个约1.2m的有效滤波值会改变判断，原始射线距离不应随阈值改变 |
| 仅alpha由.35改为.7 | 近处阶跃响应更快，静态几何和最终有效距离保持 |

参数比较使用全新处理历史或明确记录实际旧状态。不能用第一回尚未收敛的y和第二回已经收敛的y，直接推断alpha的效果。

独立挑战：为接近状态加入滞回。先给出进入和退出的两个距离阈值，画出状态转换，说明unknown如何处理，再编写代码并用原生测距验证阈值附近往返。滞回可以减少边界来回切换，EMA会引入响应延迟，两者不解决同一个问题。另一个挑战是用实际 `delta_t` 把期望时间常数转换为每帧alpha；先处理时间回退和无效帧，再讨论采样率变化，不能只替换公式而忽略状态边界。

## 诊断与验收

| 现象 | 先核对什么 |
| --- | --- |
| 共享库没载入 | 声明是否在sensor内、注册宏/基类是否匹配、实际构建日志和库路径 |
| 类型检查失败 | 父对象是否真为CPU RaySensor，不能将GPU或相机接口直接当成同一类 |
| 有主题但没新数据 | 实际源时间是否前进、世界是否暂停、传感器活动/订阅/更新率是否满足 |
| 自定义消息有值但原生扫描为空 | 原生发布是否已有订阅者、是否在比较同一源时刻，缓存查询不是新扫描 |
| 距离与中心x相差.2 | 射线击中的是前表面，不是模型原点 |
| far只剩一束有效 | 查看实际束角和方块宽度，斜束可能已经从侧面经过 |
| near后一帧仍未接近 | 用实际上帧状态计算EMA，区分算法延迟与通信延迟 |
| 无回波却沿用旧距离 | 应输出unknown并清历史，不能继续把旧值当本帧测量 |
| 修改参数结果不变 | 文件是否已重载、实际插件配置摘要是否改变 |

运行 `python3 verify.py` 或应用“验收实验”。验收应观察真实几何变化、原生消息、自定义递推、未知状态、源时间与暂停/步进，并保留原始记录。插件载入成功和JSON可以解析都只是必要条件，不代表测距处理已经正确。图形检查另外确认扫描器、目标和真实窗口；一张静态截图不单独证明频率或EMA响应。

`demo`负责在finally中恢复目标位姿，并用独立的finally恢复入口暂停状态；`verify`还用外层finally覆盖demo之后的暂停观测和步进检查，所以这些检查抛出异常时也会尝试恢复入口暂停状态。恢复请求本身失败会明确报错，不能据此宣称目标或暂停已经恢复。正常结束时二者恢复进入时的目标位姿与暂停状态；它们已经推进过真实模拟时间，不倒回EMA、回调计数、消息或时钟历史。若进入时正在运行，恢复继续后仍会产生新测量。单独的home/near/far/noecho命令则保留修改后的目标并保持暂停，供学员自己继续观察。

`python3 lab.py reset`执行全世界复位，世界模型回到各自SDF初始位姿、时钟回退；工具实际继续以等待第一段回退后的测量，确认新epoch后恢复进入时的暂停状态。它不恢复复位前的目标位置或滤波历史，也不是整体实验快照。需要全新对象、Load/Init和干净历史时使用“重载项目”。原生测量记录、软件滤波历史、模拟时钟和模型位姿分别管理，不能混为一种“恢复”。

辅助SDK进程在初始化Transport之前还会核对编译SDK完整版本必须为11.15.1；运行库DSO必须与该完整版本相同。其他Classic 11小版本不能沿用这段私有ABI兼容逻辑。退出时仍先fini，再由持有Connection的主线程Stop并join IO，最后释放通信对象；这项版本拒绝不改变插件或实验的物理更新流程。

## 原生只读请求如何等待响应

`lab.py` 每次查询会启动一份有界的原生 observer。observer 先创建本次请求的 response 订阅与 request 发布通道，再查询原生状态；发现 request 订阅者，不等于反向 response 通道已经完成连接。因此，偶发缺少响应应保留为通信失败，不能把它解释成插件状态、物理状态或课程目标本身。

`snapshot`、`entity`、`world` 的请求通道建立、连接等待和读取共同使用同一个预算，默认总计 3 秒。observer 保持同一 Node、发布者和订阅者：第一次读取只使用剩余等待预算的一半；只有等不到匹配响应时，才允许发送第二个只读请求，并使用不同的正 31 位 request ID。snapshot 每次另生成新的 nonce，要求插件原样返回。第二次读取使用原预算剩余部分，不增加总等待时间；SDK 进程初始化仍受其原有独立界限约束。

回调只接收当前 request ID 与请求类型匹配的响应，迟到的第一次响应被忽略。收到匹配响应后，必须通过 success、protobuf 类型与完整性校验；模型名须与请求相符，场景名须与本世界相符，snapshot nonce 也须一致。错误类型、错误名称、错误 nonce 或协议错误直接失败，不以再次查询掩盖。`lab.py` 的错误信息同时记录实际 mode、完整 argv 和返回码，以便区分哪次查询失败，并保留原始输出。

这项有限重试仅用于读取。暂停、继续、步进、移动和复位仍按原路径各发一次；未知修改结果不自动重发。课程的实际运动、传感器采样、计数和原始消息验收条件保持原样。独立空世界中的丢首条响应试验只能验证 SDK 请求协议，不能替代本课插件及物理目标的真实验收。
